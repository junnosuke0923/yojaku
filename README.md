# 要尺シミュレーター

服飾学校の学生が、緑のマットの上で撮った型紙の写真から、生地の必要用尺を確かめるためのWebアプリ。

撮る → 定規を合わせる → 実寸を見る → パーツを貯める → 縫い代を付ける → 生地に並べて買う長さを出す、
まで通しで動く。

写真の処理も要尺の計算も、すべてブラウザの中だけで行う。
**写真も型紙の形も、この端末から外へ出ない。** サーバーは無い。

## 動かす

```
npm install        # 最初の1回だけ
npm run dev        # http://localhost:5173 が開く
```

同じWi-Fiのスマホからも見たいときは `npm run dev -- --host` にする。
ただしそのやり方は開発中の確認用で、日常づかいには向かない
（毎回このパソコンを起動して、同じネットワークにいる必要がある）。
学生に配るのは下の「配る」のほう。

## 確かめる

```
npm run verify         # 写真から実寸に戻せるかを、合成画像で検算する
npm run verify:layout  # 縫い代・わ・区間・要尺の計算を検算する
npm run sample         # 動作確認用の写真 ../テスト用の写真.png を作り直す
npm run seed           # 開発用の「撮影ずみ」データを作り直す（下記）
```

### 撮影を飛ばして、縫い代や配置の画面だけ触る

URL のうしろに **`?dev`** を付けて開くと、最初の画面に開発用の口が出る。
押すと「もう撮り終えた状態」から始まり、そのまま縫い代の画面へ進む。
入るのは前スカート・後ろスカート・ベルトの3点。

中身は依頼者がイラストレーターで作ったスカートの図を、
**アプリとまったく同じ処理にかけて**取り出した実寸の輪郭（[src/lib/devSeed.ts](src/lib/devSeed.ts)）。
手で作った都合のいい形ではないので、実写に近い粗さのまま入っている。
図では前後スカートの定規が縦、ベルトの定規が横に置かれていて地の目の向きが違うため、
2回に分けて読んでいる（実際の撮影でも、向きの違うものは分けて撮ってもらう）。

`?dev` を付けない学生の URL には出てこない。
データも押したときにはじめて読み込む別ファイルなので、ふだんの配信には混ざらない。

`npm run verify` は、実寸が分かっている型紙をわざと斜めから撮ったように歪ませた画像を作り、
アプリの処理で元の寸法に戻せるかを見る。定規の自動判別についても、
傾き0〜35度・距離60〜160cm を総当たりして「外れた提案を出さないこと」を確かめている。

**4隅が指のぶんずれても持ちこたえるか**も、ここで見ている。
写真から実寸に直す変換は、もとは射影変換（4点をぴったり通すもの）だった。
4隅が正確なら誤差ゼロだが、指で合わせると数画素ずれ、
そのずれを「そういう遠近だった」と受け取って、定規から遠い型紙ほど大きく歪ませる。
合成画像では ±8画素のずれで最悪56%も狂った。
いまは相似変換（回転＋一様な拡大）を既定にしてあり、同じ条件で最悪2%に収まる。
検算はこの2つを並べて表示し、相似のほうが強いことを毎回確かめている。

定規1本で何枚も一度に撮る場合も、ここで確かめている。
定規は写真の**面そのもの**の実寸を決めているので、写真に1本あれば、
そこに写っているパーツは全部そのまま測れる（定規を緑の上に置いた場合と、
どれか1枚に載せた場合の両方を検算してある）。
ただし地の目の向きも同じ定規から取っているため、
**一度に撮るパーツは地の目を全部そろえて定規と平行に**置く必要がある。
この2点は撮影の画面にも書いてある。

`npm run verify:layout` は写真を使わない。実寸の輪郭から先だけを見る。
いちばん大事なのは最後の節で、**学校の配布資料に載っている目安と突き合わせている**。
マーメイドスカート③の目安【上パーツ丈+6〜10】＋【（下パーツ丈+20）×2】に対し、
同じ条件でアプリの計算が 156cm を出すことを確かめている（目安は 154〜158cm）。
自分で作った数字どうしを比べても正しさの証明にはならないので、外から来た数字と合わせている。

## 配る

学生に伝えるURLは、これひとつ。

**https://junnosuke0923.github.io/yojaku/**

置きなおすときは：

```
npm run deploy     # 検算 → ビルド → GitHub へ送る、までまとめて行う
```

検算（`verify:layout`）が落ちたらそこで止まるので、計算が壊れたまま配ることはない。
送り先は `gh-pages` ブランチで、GitHub Pages はそこを見ている（[scripts/deploy.mjs](scripts/deploy.mjs)）。

GitHub Actions（GitHub 側で自動ビルドするしくみ）は使っていない。
それには `workflow` という追加の権限が要るが、
使う端末の `gh` のログイン状態がそこまで整っていなかったため、
手元でビルドして送るこの形にした。結果は同じで、手順はこちらのほうが短い。

### 置きなおすと、古いページを開いたままの端末が壊れる（対処ずみ）

置きなおすたびに JS のファイル名が変わる（中身で名前を決めているため）。
GitHub Pages は index.html を10分ぶんキャッシュさせるので、
**スマホが古い index.html を持ったままだと、そこに書いてある名前のファイルはもうサーバーに無い。**
症状は「押しても何も起きない」「読み込みに失敗しました」で、
2026-08-27 に実機で実際に起きた（`?dev` の「撮影ずみのパーツを入れる」が失敗した）。

そのため、ビルドの日時を2か所に置いてある。

- アプリの中（`__BUILD_ID__`、`vite.config.ts` の `define`）
- `version.txt` という一行のファイル（同じく `vite.config.ts` で書き出す）

アプリは開いたとき・画面に戻ったとき・5分おきに `version.txt` を
`cache: 'no-store'` で見にいき、自分の目印と違えば
「新しい版が出ています／読み込み直す」と出す。黙って読み込み直すことはしない
（作業中に指の動きを取り上げられると困るため）。取り込んだパーツは端末に残るので、
読み込み直しても消えない。

version.txt が無い配信（開発中のサーバーや、Wi-Fi のログイン画面）は
index.html を代わりに返してくることがあるので、
**日時の一行に見えない返事は無かったことにする**。

送る前に手元で確かめたいときは：

```
npm run build      # dist/ フォルダができる
npm run preview    # できた dist/ をそのまま開いて確かめる
```

参照はすべて相対パスにしてあるので、URLにリポジトリ名の階層が付く GitHub Pages でも、
階層の付かない Cloudflare Pages でも、同じ `dist/` がそのまま動く。

スマホのカメラは `https` のページからでないと使えないため、この配り方が前提。

## 中身の構成

仕様の変更・追加が続く前提なので、画像処理・幾何計算・UI を分けてある。

```
src/lib/
  hsv.ts          色の判定。緑マットの色相を写真から推定する
  mask.ts         白黒マスクの生成、ざらつき取り、かたまりの切り分け
  contour.ts      輪郭のなぞり（Moore近傍追跡）
  geom.ts         点・多角形の基本計算、凸包、最小外接長方形、点の間引き
  homography.ts   射影変換。斜め撮影の歪みを打ち消す
  ruler.ts        定規の仕様、種類の推測、実寸への換算のしくみ
  image.ts        写真の読み込みと縮小
  pipeline.ts     上を順に呼ぶだけの流れ
  format.ts       cm / m の表示

  edges.ts        輪郭を「辺のまとまり」に切り分ける（曲がりの急なところで区切る）
  raster.ts       1mm＝1画素の白黒の絵。塗る・重ねる・数える
  seam.ts         縫い代を足して裁ち切り線を作る
  openFold.ts     「わ」の辺を鏡にして、型紙を開いた形（幅が倍）を作る
  fabric.ts       生地・折り方・区間・要尺の計算
  store.ts        貯めたパーツと生地の設定を端末の中に置く

src/components/
  Icon.tsx          アプリ全体で使う「絵ことば」。見出し・補足・ボタンの絵をここにまとめてある
  CornerPicker.tsx  定規の位置を教えてもらう。長方形のまま動かす／回す／伸ばす
  RulerToggle.tsx   50cm / 30cm の選択
  GreenTuner.tsx    緑の判定の微調整
  ResultView.tsx    実寸のシルエットと数値
  PartsView.tsx     貯めたパーツの一覧。名前・枚数
  FabricSetup.tsx   生地幅と、上下の向きの有無
  SeamEditor.tsx    辺を押して縫い代を決める
  LayoutView.tsx    生地の上に型紙を並べて、買う長さを出す
  FoldDiagram.tsx   折り方を横から見た断面図
```

ベルトや見返しのように、仮縫いのあとで寸法が変わるものは、
最初の裁断では布を裁たずに場所だけ空けておくことが多い（依頼者の指示）。
そのため「生地の上に並べる」画面には、型紙とは別に
**後で裁つぶんの余白**を置ける口がある。
写真も出来上がり線も持たない、指定された寸法どおりの長方形で、
斜線と破線で「まだ手を付けていない場所」として描き分ける。
場所は取るので、買う長さにはきちんと効く。

取り込んだパーツと生地の設定は端末の中に残るので、閉じても次に開けば続きから触れる。
そのぶん、次の課題に移るときや人に渡して試してもらうときに戻せないと困るため、
見出しの右に**「はじめから」**を置いてある（依頼者の指示・2026-08-27）。
消すと戻せないので、何がいくつ消えるのかを示して一度たずねてから消す。

「わ」の辺を持つパーツには、裁ち方が二通りある（依頼者の指示・2026-08-27）。
生地の折り山に当てて二重のまま裁つやり方と、
**型紙を「わ」の辺で開いて幅を倍にし、一重の生地に裁つ**やり方で、
布としては同じものが取れる。ベルトは後者にすることが多い。
縫い代の画面の下で選べるようにしてあり、開いたほうを選ぶと
生地の折り山は要らなくなる（型紙の中に折り山があるだけになる）。

生地の折り方は、平面図と断面図の2枚で同じことを言っている。
両側から折って**みみが中央で出会うとき**は、そこにわずかな隙間を空けて描く
（依頼者の指示・2026-08-27）。突き合わせて描くと二重の帯が1枚の面につながって見え、
そこが端どうしの出会うところだと分からなくなるため。絵のうえだけの隙間で、計算には効かない。

帯の名前は「二重」ではなく**「生地が二重」**と書く。
主語がないと、置いた型紙が2枚という意味に読めてしまうため（依頼者から実際にそう質問された）。
帯が細くて字がはみ出すときだけ短いほうに落とす。

**裏返して置いた型紙**は、白い表ではなく、うっすら斜線の入った「紙の裏」の色で描き、
「裏返し」と書き添える（依頼者の指示・2026-08-27）。形だけでは裏返したことに気づけない。

絵は全部、裁縫室にある物を横から見た形で描いてある（横棒1本＝一重、横棒2本＝二重、
ヘアピン形＝折り山、はさみ＝裁ち端、点々＝みみ）。歯車やフォルダのようなパソコンの記号と、
絵文字は使っていない。詳しくは `Icon.tsx` の先頭に書いてある。

外部の画像処理ライブラリ（OpenCV.js など）は使っていない。
読み込みが10MB近くなり、教室のWi-Fiで一斉に開くと初回が重くなるため。
必要な処理は上記のとおり自前で書いてある。

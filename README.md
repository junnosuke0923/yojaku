# 要尺シミュレーター

服飾学校の学生が、**無地で色のついた台**の上に置いた型紙を撮った写真から、
生地の必要用尺を確かめるためのWebアプリ。

撮る → 定規を合わせる → 実寸を見る → パーツを貯める → 縫い代を付ける → 生地に並べて買う長さを出す、
まで通しで動く。

写真の処理も要尺の計算も、すべてブラウザの中だけで行う。
**写真も型紙の形も、この端末から外へ出ない。** サーバーは無い。

## 動かす

```
npm install        # 最初の1回だけ
npm run dev        # http://localhost:5173 が開く
```

同じWi-Fiのスマホからも見たいときは `npm run dev -- --host` にする。
ただしそのやり方は開発中の確認用で、日常づかいには向かない
（毎回このパソコンを起動して、同じネットワークにいる必要がある）。
学生に配るのは下の「配る」のほう。

## 確かめる

```
npm run verify         # 写真から実寸に戻せるかを、合成画像で検算する
npm run verify:layout  # 縫い代・わ・区間・要尺の計算を検算する
npm run sample         # 動作確認用の写真 ../テスト用の写真.png を作り直す
npm run seed           # 開発用の「撮影ずみ」データを作り直す（下記）
```

### 撮影を飛ばして、縫い代や配置の画面だけ触る

URL のうしろに **`?dev`** を付けて開くと、最初の画面に開発用の口が出る。
入るのは前スカート・後ろスカート・ベルトの3点で、
**どこから始めるか**を3つから選べる（依頼者の指示・2026-08-27）。

- **パーツの一覧から** … 取り込んだ直後の状態
- **縫い代から** … 1枚目の縫い代の画面を開いた状態。縫い代の画面だけ見たいとき
- **並べるところから** … 生地の上に並べる画面

縫い代は既定値が入った状態で入るので、そのままでも並べるところまで進める。

中身は依頼者がイラストレーターで作ったスカートの図を、
**アプリとまったく同じ処理にかけて**取り出した実寸の輪郭（[src/lib/devSeed.ts](src/lib/devSeed.ts)）。
手で作った都合のいい形ではないので、実写に近い粗さのまま入っている。
図では前後スカートの定規が縦、ベルトの定規が横に置かれていて地の目の向きが違うため、
2回に分けて読んでいる（実際の撮影でも、向きの違うものは分けて撮ってもらう）。

一度 `?dev` で開いたら、そのあとは付けなくても出る（端末に覚えさせてある）。
スマホでホーム画面に登録したり「読み込み直す」を押したりすると `?dev` が落ちてしまい、
そのたびに URL を打ち直すことになるため。`?dev=0` で消える。

`?dev` を一度も付けていない学生の URL には、この口は出てこない。

データ（[src/lib/devSeed.ts](src/lib/devSeed.ts)）は、はじめは押したときに
別ファイルとして読みに行っていたが、**いまは本体に入れてある**。
置きなおすたびにファイル名が変わるので、古いページを開いたままの端末では
その名前のファイルがもう無く、押しても読み込めなくなっていた（実機で2度起きた）。
本体に入っていれば、どの版を開いていても必ずある。増えるのは 0.5kB 弱で、
配信の重さには関わらない。

`npm run verify` は、実寸が分かっている型紙をわざと斜めから撮ったように歪ませた画像を作り、
アプリの処理で元の寸法に戻せるかを見る。定規の自動判別についても、
傾き0〜35度・距離60〜160cm を総当たりして「外れた提案を出さないこと」を確かめている。

**4隅が指のぶんずれても持ちこたえるか**も、ここで見ている。
写真から実寸に直す変換は、もとは射影変換（4点をぴったり通すもの）だった。
4隅が正確なら誤差ゼロだが、指で合わせると数画素ずれ、
そのずれを「そういう遠近だった」と受け取って、定規から遠い型紙ほど大きく歪ませる。
合成画像では ±8画素のずれで最悪56%も狂った。
いまは相似変換（回転＋一様な拡大）を既定にしてあり、同じ条件で最悪2%に収まる。
検算はこの2つを並べて表示し、相似のほうが強いことを毎回確かめている。

定規1本で何枚も一度に撮る場合も、ここで確かめている。
定規は写真の**面そのもの**の実寸を決めているので、写真に1本あれば、
そこに写っているパーツは全部そのまま測れる（定規を台の上に置いた場合と、
どれか1枚に載せた場合の両方を検算してある）。
ただし地の目の向きも同じ定規から取っているため、
**一度に撮るパーツは地の目を全部そろえて定規と平行に**置く必要がある。
この2点は撮影の画面にも書いてある。

`npm run verify:layout` は写真を使わない。実寸の輪郭から先だけを見る。
いちばん大事なのは最後の節で、**学校の配布資料に載っている目安と突き合わせている**。
マーメイドスカート③の目安【上パーツ丈+6〜10】＋【（下パーツ丈+20）×2】に対し、
同じ条件でアプリの計算が 156cm を出すことを確かめている（目安は 154〜158cm）。
自分で作った数字どうしを比べても正しさの証明にはならないので、外から来た数字と合わせている。

## 配る

学生に伝えるURLは、これひとつ。

**https://junnosuke0923.github.io/yojaku/**

置きなおすときは：

```
npm run deploy     # 検算 → ビルド → GitHub へ送る、までまとめて行う
```

検算（`verify:layout`）が落ちたらそこで止まるので、計算が壊れたまま配ることはない。
送り先は `gh-pages` ブランチで、GitHub Pages はそこを見ている（[scripts/deploy.mjs](scripts/deploy.mjs)）。

GitHub Actions（GitHub 側で自動ビルドするしくみ）は使っていない。
それには `workflow` という追加の権限が要るが、
使う端末の `gh` のログイン状態がそこまで整っていなかったため、
手元でビルドして送るこの形にした。結果は同じで、手順はこちらのほうが短い。

### 置きなおすと、古いページを開いたままの端末が壊れる（対処ずみ）

置きなおすたびに JS のファイル名が変わる（中身で名前を決めているため）。
GitHub Pages は index.html を10分ぶんキャッシュさせるので、
**スマホが古い index.html を持ったままだと、そこに書いてある名前のファイルはもうサーバーに無い。**
症状は「押しても何も起きない」「読み込みに失敗しました」で、
2026-08-27 に実機で実際に起きた（`?dev` の「撮影ずみのパーツを入れる」が失敗した）。

そのため、ビルドの日時を2か所に置いてある。

- アプリの中（`__BUILD_ID__`、`vite.config.ts` の `define`）
- `version.txt` という一行のファイル（同じく `vite.config.ts` で書き出す）

アプリは開いたとき・画面に戻ったとき・5分おきに `version.txt` を
`cache: 'no-store'` で見にいき、自分の目印と違えば
「新しい版が出ています／読み込み直す」と出す。黙って読み込み直すことはしない
（作業中に指の動きを取り上げられると困るため）。取り込んだパーツは端末に残るので、
読み込み直しても消えない。

**「読み込み直す」は、ただのリロードではない。**
リロードでは、端末や途中の配信網が持っている古い index.html がそのまま出てくることがある
（実際にそうなった）。URL のうしろに毎回違う印（`?v=…`）を付けて開き直すことで、
同じ住所と見なされないようにしてある。印は開いたあと、履歴から消しておく。

version.txt が無い配信（開発中のサーバーや、Wi-Fi のログイン画面）は
index.html を代わりに返してくることがあるので、
**日時の一行に見えない返事は無かったことにする**。

送る前に手元で確かめたいときは：

```
npm run build      # dist/ フォルダができる
npm run preview    # できた dist/ をそのまま開いて確かめる
```

参照はすべて相対パスにしてあるので、URLにリポジトリ名の階層が付く GitHub Pages でも、
階層の付かない Cloudflare Pages でも、同じ `dist/` がそのまま動く。

スマホのカメラは `https` のページからでないと使えないため、この配り方が前提。

## 中身の構成

仕様の変更・追加が続く前提なので、画像処理・幾何計算・UI を分けてある。

```

  mask.ts         白黒マスクの生成、ざらつき取り、かたまりの切り分け
  contour.ts      輪郭のなぞり（Moore近傍追跡）
  geom.ts         点・多角形の基本計算、凸包、最小外接長方形、点の間引き
  homography.ts   射影変換。斜め撮影の歪みを打ち消す
  ruler.ts        定規の仕様、種類の推測、実寸への換算のしくみ
  image.ts        写真の読み込みと縮小
  pipeline.ts     上を順に呼ぶだけの流れ
  format.ts       cm / m の表示

  edges.ts        輪郭を「辺のまとまり」に切り分ける（曲がりの急なところで区切る）
  raster.ts       1mm＝1画素の白黒の絵。塗る・重ねる・数える
  seam.ts         縫い代を足して裁ち切り線を作る
  openFold.ts     「わ」の辺を鏡にして、型紙を開いた形（幅が倍）を作る
  fabric.ts       生地・折り方・区間・要尺の計算
  store.ts        貯めたパーツと生地の設定を端末の中に置く
  saves.ts        出した見積もりに名前を付けて、この端末の中にしまっておく

src/components/
  Icon.tsx          アプリ全体で使う「絵ことば」。見出し・補足・ボタンの絵をここにまとめてある
  CornerPicker.tsx  定規の位置を教えてもらう。長方形のまま動かす／回す／伸ばす
  RulerToggle.tsx   50cm / 30cm の選択
  GreenTuner.tsx    台の色の指定。写真の台を押す／つまみで直す
  ResultView.tsx    実寸のシルエットと数値
  PartsView.tsx     貯めたパーツの一覧。名前・枚数
  FabricSetup.tsx   生地幅と、上下の向きの有無
  SeamEditor.tsx    辺を押して縫い代を決める
  LayoutView.tsx    生地の上に型紙を並べて、買う長さを出す
  FoldDiagram.tsx   折り方を横から見た断面図
  FoldPicker.tsx    生地を上から見た小さな図。辺を押して「わ」を決める
```

### 「わ」の決め方（[src/components/FoldPicker.tsx](src/components/FoldPicker.tsx)）

> **この小さな図だけ、まだ古い描き方のまま。**
> 依頼者のイラレの図（`生地折り方_02.ai`）にもとづく描き方
> ——平らな2枚をずらして重ね、折り山の端で半円に回り込ませる——は、
> いま**大きい裁ち合わせ図にだけ**入れてある（依頼者の指示・2026-08-30
> 「まず大きな図のみを差し替えてください」）。
> 大きい図で形が決まってから、こちらへ同じ描き方を持ってくる。

もとはプルダウンで「縦わ・片側」などの**名前**から選ばせていた。
その名前は、頭の中でいったん図に直さないと選べない。
いまは生地を上から見た小さな図が出ていて、**その辺そのものを押す**
（依頼者の指示・2026-08-28）。教科書の裁ち合わせ図に添えてある折り図と同じ形なので、
学生が学校で見ているものと一致する。

押す口をこの小さな図に集めてあるのは、大きい裁ち合わせ図が
**型紙を指で引きずる場所**だから。そこに「押すと生地の構造が変わる」仕掛けを混ぜると、
型紙を動かすつもりの指が折り方を変えてしまい、並べたものが総崩れになる。
それに生地は縦に長く、下端は画面の外にあることが多い。この小さな図なら4辺とも常に見える。
ただし大きい図の**外側にある札**（「わ 折り山」「みみ」）だけは押せる。
そこは型紙と重ならない余白なので、指が迷い込む心配がない。第二の入口になっている。

さわり方は2通り。**押す**と「わ」が付いたり外れたりする。
**辺をつまんで内側へ引きずる**と、引いた深さで折る深さまで決まる
（浅ければ「型紙に合わせて」、きっちり折り切る位置の 76% まで行くとそこに吸い付く）。
引きずるほうは押すことの上位互換ではなく、「半分に折る」の選択を
ひとつの動作にまとめるためのもの。プルダウンも残してある。

#### この図が描いているのは、折りたたんだあとの面

折り山が**辺のところに来ている**のがその印である。開いた生地なら折り山は真ん中に来る。
ここを取り違えると「半分」の意味が変わってしまうので、はっきりさせておく
（依頼者の指摘・2026-08-28）。

- **片側だけ折るなら、折り返した一枚は向かい側の生地端まで行く。**
  縦わならみみからみみへ折るのだから、動いたみみは向かい側のみみの上に重なる。
  **横わも同じ**で、動いた裁ち端が向かい側の裁ち端の上に重なる
  （依頼者の指摘・2026-08-28）。落ち着いた図では、縦わのときその辺に
  点々が2本並ぶ（みみが2枚あることを表す）
- **両側から折るなら真ん中まで。** 左右（上下）の端が中央で出会う

折れる動きも、引きずったときの吸い付き先も、この位置に揃えてある（`snugDepth`）。
動く一枚の先頭も、動いている当のものを描く——縦わならみみ（点々）、
横わなら裁ち端（波）。落ち着いたあとの辺の描き方と揃っていないと、同じ端に見えない。

#### 図の大きさと、まわりの余白

図の箱は **102x110px**（1目盛り＝1px）で、その中に生地が **50x58** ある。
まわりの余白 26 は、折り山のふくらみ（10）と「わ」の字（14）を置くぶんだけで、
それ以上は取っていない。生地そのものは縦長にしてある——
実物の反物は幅より丈のほうが長いので、正方形に近い形だと布に見えない。

いちど、**折れる動きの始まり**——開いた一枚が生地の外に寝ている姿——が
丸ごと入る余白（生地の幅ぶん）を取ったことがある。
そうすると 156x142 の箱に 47x66 の絵しか入らず、空きばかりの札になってしまった
（依頼者の指摘・2026-08-28「無駄な余白をなくしましょう」）。

いまは逆にしてある。**箱を絵に合わせ、動きのほうを箱に合わせる。**
開いた一枚は、図に収まるところまでしか開かない（`flipFrames` の `k`）。
**着地する先は変えていない**ので、「向かい側の生地端まで折る」ことは
そのまま見て取れる。大事なのはどこへ着くかで、どこから始まるかではない。

箱の高さ（110）は、となりに並ぶ文字の段の高さに合わせてある。
どちらかが高いと、低いほうの下に空きが出る。この直しで札は 156px から 124px になった。

**片わは上下左右どの辺でも作れる**（依頼者の指示・2026-08-28）。
前中心が「わ」で後ろ中心はそうでない、という場面は実際にある。
そのとき現実では右側を山折りにして、そこに前中心を当てる。
左を「わ」にして型紙を裏返しても布としては同じものが取れるが、
このアプリは**実際の裁断の下稽古**でもあるので、現場で踏む手順のほうを採る。
そのため折り方には `vRight`（縦わ・右）がある。
折りのしくみは初めから「どの辺か」で動いていた（`foldSidesOf` が辺の組を返す）ので、
断面図も大きい裁ち合わせ図も、手を入れずにそのまま右側に対応した。

#### 折れる動き

辺を押して「わ」が付いた瞬間だけ、外に開いていた一枚が
折り山を軸に**起き上がって内側へ倒れてくる**。

ここは一度やり直している。初めは 260ms で、線だけの一枚を裏返していた。
それでは「折れる動作というのが見て取れない」（依頼者・2026-08-28）。
直したのは3つ。

- **760ms** に伸ばした。倒れるのに7割を使い、倒れ切ったところでいったん止めてから消える。
  止める間があると、そこが「折り終わったところ」だと分かる
- **生地と同じ色で塗り、下に影を落とす。** 色を変えれば目立つが、
  どの折り方でも生地の色は変えない決まりがある（依頼者の指示・2026-08-27）。
  そこで色ではなく影で浮かせた。影は動いている間だけで、落ち着いた図には残らない
- **途中の姿**を挟んだ。裏返すだけでは、線が横に滑ったようにしか見えない。
  折っている途中の紙は立ち上がってこちらに近づくので、途中では軸の向きに潰しつつ
  軸と直角の向きには少し大きくし、わずかに持ち上げる（`flipFrames` の `mid`）

引きずって折ったときは動かさない。指がもう動かしたあとなので、重ねる意味がない。
動きを控えめにする設定の端末では、動かさずに結果だけ出る。

ベルトや見返しのように、仮縫いのあとで寸法が変わるものは、
最初の裁断では布を裁たずに場所だけ空けておくことが多い（依頼者の指示）。
そのため「生地の上に並べる」画面には、型紙とは別に
**後で裁つぶんの余白**を置ける口がある。
写真も出来上がり線も持たない、指定された寸法どおりの長方形で、
斜線と破線で「まだ手を付けていない場所」として描き分ける。
場所は取るので、買う長さにはきちんと効く。

画面のいちばん上の**段階の帯は、前へも後ろへも通れる道**である
（依頼者の指示・2026-08-27）。押せるかどうかを決めるのは
「その段階で見せるものが、もう揃っているか」だけで（`App.tsx` の `canGo`）、
揃っていれば行ったり来たりできる。
写真も定規もまだ、という段階は、行っても何も無いので押せないままにしてある。

**先へ進むほうも押せる**ようにしたのは、依頼者の指示による。
たとえば並べている途中で、縫い代を一本だけ直してまた続きへ戻る——
という往復ができないと、直すたびに前の画面をひとつずつたどり直すことになる。
取り込んだものも並べたものも `parts` にまとめて持たせて端末に残してあるので、
画面を行き来しても、直したところは直ったまま戻ってくる。
縫い代を広げれば、並べる画面の型紙もその場で広がる。

帯の上の細い線は3通りに塗り分ける。
濃い緑＝ここまで来た、薄い緑＝押せば行ける、灰色＝まだ行けない。

取り込んだパーツと生地の設定は端末の中に残るので、閉じても次に開けば続きから触れる。
そのぶん、次の課題に移るときや人に渡して試してもらうときに戻せないと困るため、
見出しの右に**「はじめから」**を置いてある（依頼者の指示・2026-08-27）。
消すと戻せないので、何がいくつ消えるのかを示して一度たずねてから消す。

このボタンが消すのは、**いま出ている画面のぶんだけ**（依頼者の指示・2026-08-27）。
並べる画面で押したときは、並べた場所だけを置く前に戻し、
取り込んだパーツも生地の設定もそのまま残す。
以前はどの画面から押しても全部消していたため、
「置きなおしたいだけ」で押した結果、撮るところからやり直しになった。
たずねる文面も、その画面で実際に消えるものと残るものを書き分けてある。

ここで出るのは**概算**である、と2か所に書いてある（依頼者の指示・2026-08-28）。
撮る前の画面のいちばん上と、買ってくる長さが出たすぐ下。
数字を見てから初めて知るのでは遅いので、始まりにも置いてある。
型紙の形は写真から読み取っているので実物とは数ミリの差が出るし、
地直しの縮みや柄合わせ、裁つときのくせでも変わる。
ひと言だけ出して、理由は「？」の中に畳んである。

買ってくる長さは、並べる画面の**いちばん下**に置いてある（依頼者の指示・2026-08-27）。
上にあると、まだ何も並べていないうちから結果が目に入って、
「並べる → 長さが出る」という順に読めない。
「置くパーツ」のすぐ下なので、1つ置いて目を下ろせば、そのたびに変わるのが見える。

出した見積もりは、名前を付けて**しまっておける**（依頼者の指示・2026-08-28）。
しまうのは結果の数字だけではなく**作業まるごと**——
型紙・縫い代・生地の設定・並べ方まで（依頼者の選択）。
数字だけにすると、あとで見て直したくなったときに何もできない。
まるごと持たせておいて、一覧に出すぶん（買う長さ・生地幅・日付）だけを
`summary` に取り出してある。

置き場所は**この端末の中だけ**（依頼者の選択）。
ファイルにも画像にも書き出さない。学校の管理端末で使うものなので、
写真から取った型紙の形も、この端末から出ない。

しまう口は並べる画面の下（買う長さのすぐ後ろ）、開く口は撮る画面。
撮るボタンより下に置いてある。ふだんの入口は「撮る」なので、
上に積むと毎回それをまたぐことになる。ふだんは最近の3件だけ出す。

同じ名前でしまうと**書きかわる**。名前がそのまま行き先になるので、
「同じ名前＝同じもの」と読めるほうが分かりやすく、
「新しくしまう」のか「上書きする」のかを学生に考えさせずに済む。
開いたものは名前の欄に名前が入った状態で戻ってくるので、
直してもう一度しまえば、増やさずにその場で書きかわる。

しまえる数は20件まで（`MAX_SAVES`）。1件に型紙の輪郭がまるごと入るため、
際限なく増やすとブラウザの置き場所が尽きる。
尽きたときに黙って消えるのがいちばん困るので、先に上限で止めて知らせる。
座標は 0.1 mm きざみに丸めてからしまう。それより細かい桁は裁つときに意味を持たないのに、
置き場所だけはその桁のぶんきっちり食う。

開くと、いま触っているぶんは置きかわる。戻せない操作ではない（下の控えに積まれる）が、
黙って置きかえると何が起きたのか分からないので、作業中は一度たずねる。
消すほうは戻せないので、必ずその行の中でたずねてから消す。

作業中はいつでも **1つ戻る／1つ進む**が使える（依頼者の指示・2026-08-27）。
見出しの右、「はじめから」の隣にある。
戻せるのは取り込んだパーツ・縫い代・生地の設定・並べた位置で、
つまり画面をまたいで戻る（縫い代を付けたあと並べる画面へ進んでも、縫い代まで戻れる）。

しくみは単純で、**変わるたびに全部の控えを1つ取っておく**だけ。
どの画面も `updateParts` という一箇所を通るので、画面ごとの書き分けが要らない。
控えは40回ぶんで、古いほうから捨てる。

型紙を指で引きずっているあいだは、途中の位置をいちいち控えない。
1回の引きずりに**合図（`drag1`, `drag2`, …）を付けて**、同じ合図が続くあいだは
控えを積み増さないようにしてある。はじめは「前の変化から◯ミリ秒以内なら同じ操作」と
時間で見ていたが、生地を長くすると1回の描き直しに1秒近くかかることがあり、
そのやり方では毎回まとめ損ねた（実測で8回の移動が7.9秒）。時間に頼らない形にしてある。

### 「わ」の辺は、引きずるだけで折り山に付く（[src/lib/fabric.ts](src/lib/fabric.ts) の `foldEdgeSides`）

**「わ」の辺を折り山のそばまで持っていけば、そのまま吸い付く**
（依頼者の指摘・2026-08-31「手動でわの折り方の部分に持っていった際は自動で吸着して欲しい。
現状だと下部に出てくるボタンを押さないとわに当てた判定になっていない」）。

もともと「折り山に当てているか」は、位置から求めず `snapTo` という**状態**として持っている。
位置から判定しようとすると、面の幅は折りの深さで決まり、折りの深さは面の幅で決まる、
という堂々めぐりになるためで、この持ちかたは変えていない。
変えたのは**その状態を誰が立てるか**で、いままではボタンだけだったところに、
引きずる操作からも立つようにした。並べるのは手でやる作業なので、
手の動きのほうが本筋であり、ボタンは控えになる。

当てる先は、その型紙の「わ」の辺が**向いている側だけ**に絞る（`foldEdgeSides`）。
近いというだけで吸い付かせると、縦に走る「わ」の辺が上の折り山に当たる、という
実物ではありえない置き方ができてしまう。向きは「わ」の記号が持っている3点
——辺に沿った2点と、型紙の内側の1点——から出す。本体が辺より右にあれば、
その辺は左を向いている。回しても裏返しても同じ計算で通る。

離すのも同じ規則で、吸い付く範囲から出れば当たっていない状態に戻る。
外すためにボタンを押しに行かなくてよい。
吸い付く幅は生地幅の 5%（最小 3cm）で、細い生地でも太い生地でも画面上は同じ幅に見える。

吸い付くかどうかを決めるのは、**指が示した位置のほうで、実際に落ち着いた位置ではない**。
両端が出会うまで折ってあるときは、出会い目をまたげないので置ける場所が半分ずつに限られ、
そちらで判定すると折り山から離れられなくなる。

これに合わせて、状態が立つ入口を2つ足してある。どちらも
「見た目は当たっているのに、当てていないことになっている」を消すためのものである。

- **置いた瞬間**（`place`）… 「わ」つきの型紙は、置いた先に向きの合う折り山があれば当てる
- **折り方を変えた瞬間**（`onFold`）… 「置く → 折り方を決める」の順に触ったとき、
  折り方を決めたのに注意書きが残る状態にならないようにする

つかむ位置も直した。折り山に当てている向きは位置を折り山から決めているので、
`xMm` には当てる前の古い値が残っていることがある。
引きずりはじめの位置は、置いてある値ではなく**いま図に出ている位置**（`report.boxes`）から取る。

#### 控えのボタンも、同じ規則で絞る（`snapTargetsOf`）

引きずるほうだけ向きを見ていて、**ボタンのほうが野放しだった**（依頼者の指摘・2026-08-31）。
折り山がある辺すべてに札を出していたので、「わ」の辺が左を向いている型紙にも
「わに当てる（右）」が出ていたし、そもそも「わ」の辺を1本も持たない型紙にまで出ていた。
押しても向きは合わないので、生地の端に寄るだけで折り山には当たらない。
いまは `snapTargetsOf` を通し、引きずるときとまったく同じ絞り込みをしてから札を出す。

ただし、**いま当てている辺だけは必ず残す**。当てたあとで型紙を回すと向きが変わるので、
絞り込んだだけだと札が消えて、当てっぱなしから抜けられなくなる。

#### 回したら、当てる先を付け直す（`resnap`）

どの折り山に当てられるかは「わ」の辺の向きで決まるのだから、型紙を回せば当然変わる。
ところが当てた先だけが古いまま残っていたので、
**「わ」が右を向いているのに左の折り山に当たっている**という、実物では起こりえない図が描けた。
いまは置き場所を書き換えるところ（`patch`）を必ず `resnap` に通し、
向きが合わなくなったら合う折り山へ付け替え、合う折り山が無ければ外す。
外れたときは「折り山に当ててください」が出るので、置き直す入口になる。

### 台の色と、取り込むものの選択（[src/lib/hsv.ts](src/lib/hsv.ts) / [src/components/GreenTuner.tsx](src/components/GreenTuner.tsx) / [src/components/ResultView.tsx](src/components/ResultView.tsx)）

#### 台は緑でなくてよい

型紙の切り抜きは**色だけ**で行っている。形は見ていない。
写真でいちばん多い色を「台の色」とみなし、そこから外れた画素を型紙として拾う。

はじめは裁断室の緑のマットだけを想定していたので、
自動推定も手動のつまみも**色相 60〜210度（黄緑〜水色）に縛って**いた。
その外に山が立つと「推定に失敗した」とみなして緑へ戻していたので、
暖色の台は、手で指定することすらできなかった。

いまはこの縛りをやめてある（依頼者の指示・2026-08-31
「必ずしも緑のマットの上で撮れるかどうかは分からない」）。
学校の裁断室以外——教室の机、自宅——でも撮ることになる以上、
紺の布・赤い風呂敷・オレンジの下敷きのような台も使えるべきである。
型の名前が `GreenParams` のままなのは古い名残りで、緑という意味はもう無い。

**色がついていない台（白い机・木目の机・灰色）は、いまも分けられない。**
鮮やかさの低い画素は「色がない＝型紙」と判定するので、机ぜんぶが型紙に化ける。
これは判定のしかたの限界であって、直しかたは「無地で色のついた布か紙を1枚敷く」しかない。
そのことを、うまく拾えなかったときの案内に書いてある。

#### 台を1回押して、色を教えてもらう

つまみは4本（色あい・許容幅・鮮やかさの下限・明るさの下限）あるが、
**4本動かして色を当てにいくのは学生の仕事ではない。**
そこで、つまみより先に**写真そのものを出して、台を1回押してもらう**道を上に置いた
（依頼者の指示・2026-08-31）。

押された点の周り 5×5 画素をならしてから HSV に直し（`sampleHsv`）、
色あいだけでなく鮮やかさと明るさの下限も**その点より下**に置く（`pick`）。
下限まで一緒に決めるのは、淡い台や暗い台だと、色あいが合っていても
下限に引っかかって台ぜんぶが型紙に化けるためである。
押した点は必ず台の側に入る、という形にしてある。

#### 取り込むものは、こちらで捨てずに選んでもらう

型紙以外のもの——消しゴム、紙片、はさみ——も、台の色でなければ型紙として拾われる。
`MIN_AREA_RATIO = 0.0015` と実寸10mmの下限があるので、
**おおよそ3cmより大きいものは全部**この画面に出てくる。

これを自動で捨てる案は採っていない。
「細長いから型紙ではない」といった判定は、
バイアステープや持ち出しのような本物の細い型紙を黙って捨てるし、
「これは消しゴムです」と機械が名指しするのは、学生向けの道具として出せない
（確信の持てない自動判定を名前として画面に出さない、という約束事）。

かわりに、結果の一覧の**カードを押すと外れる**ようにしてある
（`App.tsx` の `excluded`、`ResultView` の `PartCard`）。
外したカードは薄くなり「取り込みません（押すと戻ります）」に変わり、
写真の上の輪郭も破線になる。取り込むボタンの文字も
「選んだ 3 個を取り込む」に変わるので、押す前に数で確かめられる。
全部外すとボタンは押せない。

#### 拾えなかった型紙の逃げ道

どうしても切り抜けない型紙は、**長方形として手で入れる**道がある。
もとは「ベルト・見返し・カフス・衿」のような後裁ちのパーツのために作った入口だが、
実物にメジャーを当てて幅と丈を「その他」で入れれば、要尺の見積もりとしては足りる。
そのことが分からないと逃げ道にならないので、
その入口の「？」の中に書き足してある（依頼者の指示・2026-08-31）。

## 画面の文章について

説明は**既定で短く**する（依頼者の指示・2026-08-27。
「説明文がやたら長かったり多かったりして、あまり感覚的にやれない」）。

常に出しておくのは、それだけで意味が通るひと言だけにして、
理由や例外は「？」の中に畳む（`Icon.tsx` の `Hint`）。
情報は減らさず、**見えている量だけを減らす**。分からなくなった人の逃げ道は残す。
畳んだ説明を開く的は行そのものなので、小さな「？」印を狙う必要はない。

図の下に長い文を置かないことも同じ理由。絵より先に文を読ませてしまう。
断面図の下にあった一文は落とした（依頼者の指示・2026-08-27）。
「二重」「一重」「わ」「みみ」は絵の中に書いてあり、同じことを文でもう一度言っていた。
まだ折っていないときだけは、何をすれば折れるのかを短く添える。

**同じ絵をいくつも並べない**（依頼者の指摘・2026-08-27。
「縫い代を示したピクトグラムが同じものがそこら中にある」）。
絵は、あるだけでその場所の意味を言うものなので、
同じ絵が1画面に3つあると、どれも意味を持たなくなる。
縫い代の画面では、はさみ・縫い代の絵を、見出しの1つに絞ってある
（補足の行は「？」の印、「まとめて」の行は文字だけ）。

同じ理由で、**同じ絵に二通りの意味を持たせない**。
「しまっておく」にはしおりの絵（`save`）を新しく足してある。
並べる画面には「後で裁つぶんの余白（`hold`）」が先にいるので、
そこで絵を使い回すと、ひとつの画面で同じ絵が二つのことを指してしまう。

この方針に直したときの文字数は、撮る 307→156、パーツ 556→396、並べる 777→448。

### はじめて開いたときの案内（[src/components/Tour.tsx](src/components/Tour.tsx)）

**いまは止めてある**（`TOUR_ON = false`。依頼者の指示・2026-08-27）。
機能の直しと画面の調整がこの先も続くあいだは、案内の文面と実物が食い違いやすく、
画面を変えるたびに文面も直すことになるため。画面が固まってから出す。
仕組みそのものは動く状態で残してあるので、`TOUR_ON` を `true` にすれば戻る。
そのときは、案内と同じことを言っている常設の説明（パーツ一覧の
「枚数はできあがりに必要な数」）を、もう一度消すこと。

以下は、出すようにしたときの話。

説明を減らすほど、はじめての人の手がかりも減る。
その埋め合わせに、**最初の1回だけ、実際の部品を光らせて順に説明する**
（依頼者の提案・2026-08-27。「代わりに初回時には、各項目を照らしながら
説明するチュートリアルを入れる」）。

- 案内は画面ごと（撮る・パーツ一覧・縫い代・並べる の4本、合計14項目）。
  その画面を**はじめて開いたときだけ**出て、読み終えると二度と出ない
- 読んだかどうかは端末に覚えさせる（`yojaku.tour1.<画面>`）。
  中身を書き替えたときは `Tour.tsx` の `KEY` の番号を上げると、もう一度出る
- 見出しの「？」でいつでも呼び戻せる。1回きりで消えるものに、逃げ場を残すため
- 指す相手は `data-tour="…"` で印を付けてある。
  その画面に無い部品（縫い代つきの型紙には「まとめて」が無い）は、だまって飛ばす
- 書く相手は学生。「わ」「地の目」「みみ」といった言葉そのものは説明しない。
  説明するのは、どこを押せば何が起きるか、だけ

案内があるぶん、**同じことを言う常設の説明は消してよい**。
パーツ一覧の「枚数はできあがりに必要な数」がその一例で、
消すと一覧がちょうど1画面に収まる（案内を止めているいまは戻してある）。

縫い代は、辺のまとまりごとに帯を塗り足して作る（[src/lib/seam.ts](src/lib/seam.ts)）。
このとき**線分の向きは、その線分が属する辺の中だけを見て決める**。

輪郭は3mm間隔で取り直してあるので、角のちょうど上に点が乗るとはかぎらない。
角をまたぐ線分が1本でき、その向きは両側の辺の中間になる。
そのまま法線を取ると、裾のような広い縫い代のときに角が斜めに張り出したり削げたりする
（実際に裾を4cmにして起きた・依頼者の指摘・2026-08-27）。
辺の内側の点だけで向きを測れば、角は実物どおり四角く決まる。
角の点そのものは両方の辺に半分ずつ乗っているので、向きの測定からは外している。

縫い代の札は「わ」ではなく**「わ 0」**と書く（依頼者の案・2026-08-27）。
「わ」と「縫い代 0」が同じことだと、札そのものが言っているので、
文で説明する必要がなくなる。説明を減らすときは、
消した内容を札に移せないかを先に考えること。

**どの画面も、できるかぎりスマホの1画面に収める**（依頼者の指示・2026-08-27）。
下へスワイプしないと操作できない状態は、それだけで使いにくい。

375×812 で測ったはみ出しは、撮る 0・パーツ一覧 21（3個のとき）・縫い代 0・並べる 636。
パーツ一覧の 21 は、案内を出すようにして「枚数」の説明を消せば 0 になる。
並べる画面だけは、生地の絵そのものが 1.5m ぶんの長さを持っているので収まらない。
ここは段の間隔を詰めるにとどめてある。

縫い代の画面は、その中でもきちんと収まるように組んである。
下へスワイプしないと操作できない状態は、それだけで使いにくいため。

- 戻る・型紙の名前・隣の型紙への送りを、いちばん上の1段にまとめてある
- 「まとめて」と「1本ずつ」は、もとは別々の枠だったが、ひとつの枠に入れてある
- 図の高さの上限は `max(140px, min(34vh, calc(100dvh - 33rem)))`。
  「画面の高さから、下の操作のぶんを引いた残り」なので、
  小さい端末では図のほうが縮んで、収まった状態を保てる。
  縮みすぎると辺を押せなくなるので下限も置いてある
- 「わ」の裁ち方を選ぶところも1段。説明は、ふつうでないほう（開いて裁つ）を
  選んだときにだけ出す

縫い代の幅は、よく使う値を札にして並べてあるが、
**札に無い数値を直接入れる欄**も下に置いてある（依頼者の指示・2026-08-27）。
1.8 cm のような指定が出たときの逃げ道で、1 mm 刻みに丸める。
札を増やすと、いつも使う 1 cm や 1.5 cm が探しにくくなるため、
めったに使わない数値はこちらへ回す。
いま入っている幅が札のどれでもないときは、この欄を縫い代の色にして、
その数字がどこから来たのかが分かるようにしてある。
なお「まとめて全部に付ける」ほうは、決まった一覧のままにしてある。

送りは右上（依頼者の指示）。1枚ごとに一覧へ戻るのは手間なため。
最後の1枚まで来たら、そのまま並べるところへ進める。

**「わ」に指定した辺には、作図の記号を辺そのものに付ける**
（依頼者の指示・2026-08-27）。◎ を半分にした形——同じ中心の半円を二重に、
平らな側を辺に伏せ、まるいほうを型紙の内側へふくらませて描く（`SeamEditor` の `foldMark`）。
学校の作図で「この辺は折り山（わ）」を表す決まった印なので、
文字より先にこの形で読み取れる状態にしておく。
辺に沿う向きを `t = (outward.y, -outward.x)` に取ると、
SVG の弧を `sweep=1` で引くだけで内側へふくらむ。
番号のふきだしに添える「わ」の字は、記号と重ならないよう外向きへ押し出してある。

**この記号は、生地に並べた図にも出す**（依頼者の指示・2026-08-27）。
むしろ裁ち合わせ図のほうが本番で、どの辺を折り山に当てているかが図の要になる。
そのため `PlacedPart` は `foldMarksMm` を持つ。辺ごとに **3つの点**
（辺に沿った直径の両端 a・b と、型紙の内側の点 inn）で置き場所と向きを表したもので、
`a`–`b` の長さは `FOLD_MARK_REF_MM` に固定してある。実際に描く大きさは描く側が決める。

向きを角度や法線で持たずに点で持たせてあるのには理由がある。
生地の上では型紙を回したり裏返したりするので、
点にしておけば `orientedPair` の中で裁ち切り線とまったく同じ計算に通せて、
**裏返したときに弧のふくらむ向きが反転する**という間違いが起こらない。
弧のまわり方（SVG の sweep）は `(b - a) × (inn - a)` の符号から毎回決める。
`verify:layout` に、そのまま・裏返し・180度・地の目90度の4通りで
まるいほうが型紙の内側を向いているかを見る検算を入れてある。

「わ」の辺で開いて裁つ設定にしたパーツは、生地の折り山に当てないので記号も出さない。

「わ」の辺を持つパーツには、裁ち方が二通りある（依頼者の指示・2026-08-27）。
生地の折り山に当てて二重のまま裁つやり方と、
**型紙を「わ」の辺で開いて幅を倍にし、一重の生地に裁つ**やり方で、
布としては同じものが取れる。ベルトは後者にすることが多い。
縫い代の画面の下で選べるようにしてあり、開いたほうを選ぶと
生地の折り山は要らなくなる（型紙の中に折り山があるだけになる）。

開いたほうを選ぶと、型紙は本当に「わ」の線を軸として反転し、幅がちょうど倍になる
（`openFold.ts` の `unionWithMirror`。ベルトの例で 26.1 cm → 52.0 cm）。
ただし**開いた形には、中心を示す一点鎖線が要る**（依頼者の指摘・2026-08-28）。
線が無いと、ただ幅の広い長方形にしか見えず、
反転して倍になったことが図から読み取れない。実際そう見えるという指摘を受けた。
しくみは正しく動いていても、**図がそう言っていなければ、まだ届いていない**。

そのため `PlacedPart` は `centerLineMm` を持つ。もとの「わ」の辺を
出来上がり線の外接まで伸ばした線分で（`geom.ts` の `clipLineToBox`）、
「わ」の記号と同じく `orientedPair` の中で裁ち切り線と同じ計算に通す。
描くのは縫い代の画面の下の見本と、生地に並べた図の両方。
一点鎖線（長・短・長…）は作図で中心線を表す決まった引き方なので、
出来上がり線（実線）とも縫い代（別の色）とも読み分けられる。

中心線は型紙の真ん中を通り、地の目線もふつうは真ん中を通るので、
**そのままだと2本がぴったり重なって読めなくなる**。
2本が平行になるときだけ、地の目線を型紙の幅の2割ほど脇へどける
（`LayoutView.tsx` の `grainShiftOf` と `PatternMarks` の `shift`）。
直角に交わるときは1点で交わるだけなので、どけない。

生地の**上下の端はどちらも波線**で描く（依頼者の指摘・2026-08-27）。
どちらもはさみで切った裁ち端なので、下だけまっすぐに引くと折り山に見えてしまう。
折り山にする側だけは、波線ではなくまるみのある角で描き分ける。

**二重になっているところは、下の一枚を2方向にずらしてのぞかせる**
（依頼者の指示・2026-08-27）。折り山の反対側へ少し出すだけでは、
重なっている感じが伝わりにくい。折り山に沿う向きにも `RIM * 1.15`（`UNDER_SHIFT`）
だけずらして、紙を2枚わずかにずらして重ねたときのように角をのぞかせる。
ずらす量は控えめにすること。大きくすると、折り返しではなく
「2枚の別の布」に見えてしまう（依頼者と何段階か見比べて決めた値・2026-08-27）。
下の一枚のみみ（点々）は、**実際にのぞいている側にだけ**描く。

#### 端だけ折り返したときも、下の一枚を描く

**折ってあるなら、下の一枚はいつも描く**
（依頼者のイラストレーターの図 `生地折り方_02.ai` の5〜8ページ目・2026-08-31）。

以前は「面が丸ごと二重のときだけ」に絞っていた。
端だけ折り返したときに2枚目を描くと、生地ぜんたいが二重に見えてしまう、
と考えたためである。ところがいただいた図はそうなっていなかった。
**折り返して上に乗っている一枚を明るく（`CLOTH`）、その下から出ている一枚を
暗く（`CLOTH_FOLDED`）**塗ってあるので、
「明るいところ＝上にもう一枚乗っている＝二重」と読める。

この描き分けは、折り返しの山が U 字に回り込んで見えるためにも要る。
回り込みは**上の一枚と下の一枚が同じ頂点（`leadApex`）に集まる**ことで
半円になるので、下の一枚が無いと回り込む相手がいない。
端だけ折り返した図に円弧が出ていなかったのは、これが理由だった。

そのために、上の一枚（`topPath`）は**折り返したぶんだけ**の一枚として描く。
面ぜんぶを上の一枚で描いていると、折り山の端に相手がおらず、
折り返しがただの色の境目になる。
みみの帯は面の外側にあるので、折り返した一枚の端も `SEL_BW` ぶん外まで伸ばす。

下の一枚は、いただいた図では上の一枚に対してずらしてある。
**そのとおりにすると、型紙を置ける面そのものがずれてしまう**ので、
ずらすのではなく、**のぞく側だけ `UNDER_SHIFT` 伸ばす**
（縦わなら下へ、横わなら右へ）。見た目は同じで、
`[0, W] × [0, L]` の面は動かないので、端に寄せた型紙が生地から浮くことがない。

折り返した端に落としていた影は、このときは描かない。
色の違いだけで「ここから先は一重」と分かるうえ、
影を重ねると同じ生地が折り方によって違う色に見えてしまう。

絵の下のひと言も入れ替えた。以前は「濃いところが二重」だったが、
新しい描き方では逆で、**白いところが二重、濃いところが一重**である。

#### 2枚の輪郭は、うすい線で引く

折り返した一枚と下の一枚は色の差がわずかなので、
線が無いと境目——とくに折り山の回り込み——がどこにあるのか読めない。
`topPath` と `underPath` の両方をうすい線（`#b8b6a4`）でなぞる。
折り返した端に個別に引いていた線（縦わの直線・横わの波線）は、
この輪郭に含まれるので取りやめた。同じ端に2本の線が乗ると、
波の刻みがわずかにずれて二重に見えてしまう。

#### みみの帯の、引き方

依頼者がイラストレーターで描いた図（`生地折り方.ai`・2026-08-30）に合わせて、
みみは **幅のある帯**として引く。帯の内側には境目の線を一本入れる。
点々だけだと「そこに幅のある帯がある」ことが伝わらず、
生地の面とみみの区別が付かない。色や素材感はこれまでのものをそのまま使う
（参考図は「形」の指定であって、色の指定ではない）。

帯の引き方には、守るべきことが3つある。

1. **その一枚の端から端まで届かせる。**
   上の一枚の帯は上の一枚の裁ち端まで、下の一枚の帯は
   下の一枚の裁ち端まで。途中で途切れていると、
   そこで生地が終わっているように見える（依頼者の指摘・2026-08-30）。
   下の一枚はずらして描いてあるので、上の一枚とは長さも位置も違う。
2. **折り山を回り込むところも続ける。**
   横わのとき、みみは折り山の上を 180 度回って向こうへ続いている。
   山の手前で帯が止まると、回り込んでいることが形で見えなくなる。
3. **点々の位置は図ぜんたいで共通の格子で決める。**
   帯の始まりから数えると、上の一枚と下の一枚で点の高さがずれ、
   2列が別々のものに見える。そろえていれば「同じ生地のみみが2枚」に見える。

帯をどこで止めるかは、座標ではなく**その一枚の形で切り抜いて**決める
（`${gid}-clip` と `${gid}-clip-under`）。折り山の角は丸く、
裁ち端は波打っているので、端の位置を数式で追うとすぐに合わなくなる。
長めに引いておいて形で切るのが、どの折り方でも崩れない。

#### みみも、折り山の端でいっしょに回り込む

**横わのときは、みみの帯も回り込みの円弧に沿って曲げる**
（依頼者の指摘・2026-08-30「耳もやはり折り返しの円弧に沿ってカーブしないと
自然に見えません。イラストレーターのデータでもそのようにしていました」）。

もとはまっすぐな帯（`<rect>`）を長めに引いて、その一枚の形で切り抜いていた。
輪郭は回り込んでいるのに帯はまっすぐなので、みみが回り込みのところで
ぶつ切りになって見えていた。

イラレの図（生地折り方_02 の3ページ目・パス 23／25／28）を見ると、
みみの線は**輪郭の回り込みを内側へ平行移動した形**になっている。
平行曲線ではなく平行移動なので、`sheet()` と同じ `turnTo()` に
x をずらした座標を渡すだけで同じ形になる（`selvagePath()`）。

帯・内側の線・ピン穴の3つとも、同じ道に沿った `<path>` の**線**として引く。

- 帯 … 幅 `SEL_BW` の線を薄く
- 内側の線 … 細い線
- ピン穴 … `strokeDasharray="0 ピッチ"` ＋ `strokeLinecap="round"`。
  長さ0の破線を丸い端で描くと点になり、**曲線のところでも粒が道に乗る**。
  イラレの図でも破線で描いてある

折り返して面の上に乗っている一枚のみみ（`selvageStraight()`）だけは、
面の内側にあって回り込みが無いので、まっすぐのままでよい。

#### みみは、型紙を置ける面の**外側**に描く

**みみの上に型紙は乗らない**（依頼者の指示・2026-08-30
「耳は裁断の時に使わないので、耳の上にはパターンは乗らないでください」）。

計算のうえでは、生地幅からみみを引いたものが型紙を置ける幅
（`usableWidthMm()` ＝ `widthMm - SELVAGE_MM * 2`）で、
図の `W`（`surfaceWidthMm`）はその置ける幅そのものである。
それなのにみみの帯を `[0, W]` の**内側**へ描いていたので、
端に寄せた型紙がみみの上に乗っているように見えていた。

そこで生地の外形だけを、みみのぶんだけ外へ広げる。

```
bx0 = 左がみみの側なら -SEL_BW、折り山の側なら 0
bx1 = 右がみみの側なら W + SEL_BW、折り山の側なら W
```

型紙の座標（`[0, W]`）はいっさい動かさない。動かしたのは**生地の絵の外形だけ**で、
これで図に描いてある生地がちょうど生地幅ぜんぶになり、
「みみは使わない」ことが絵のうえでも本当になる。折り山の側にみみは無いので広げない。

同じ理由から、

- 折り返して面の上に乗っている一枚のみみ（`selvageStraight()`）は、
  折り返しの端から**外側**（折り山から離れる向き）へ引く。
  内側へ引くと、その折り返しに「わ」で当てて置いた型紙の上にみみが乗る
- 両側から折ってみみが中央で出会うときの隙間 `MEET` は、**みみ2枚ぶんの幅**
  （`SEL_BW * 2`）にしてある。そこで出会っているのは左右のみみそのものなので、
  2本の帯がちょうど隙間に収まり、どちらの折り返しの上にもはみ出さない

#### みみとみみが出会うところは、わずかに開ける

両側わ（縦わ・両側）で中央に出会っているのは、左右の**みみそのもの**。
そこで `MEET_V` は **みみ2本ぶん＋そのあいだのわずかな隙間**（`SEL_BW * 2 + SEL_GAP`）にしてある。
実物は突き合わせでも、図としてはわずかに開けておくほうが、
みみが2本あることが分かる（依頼者のイラレの図・2026-08-30）。

みみの帯を暗い色の上に乗せると、その2本だけ他の折り方より濃く見えてしまうので、
みみとみみが出会っているところには折り返しの影も落とさない。
裁ち端どうしが出会う横わ・上下は事情が違うので、隙間は別の定数（`MEET_H`）にしてある。

#### 端どうしが出会うとき、上の一枚は「2枚」である

隙間を、下の一枚の色で塗った長方形として描いていたことがある。
それだと隙間の上端でも下端でも裁ち端の波がつながってしまい、
1枚の布が真ん中に線を持っているようにしか見えなかった
（依頼者の指摘・2026-08-30「開けたところは下側が覗いているようにしないといけない」）。

**上に来ている一枚を、2つの別の布として描く。**
`topPath` を、出会い目の手前で切った2つのパス（`sheet()` を2回呼ぶ）にする。
`sheet()` には「どの辺が折り山か」を渡せるようにしてあり、
左半分には `['left']`、右半分には `['right']` を渡す。
すると波もそこで切れ、隙間には**本当に穴が空く**。
下の一枚はずらして敷いてあるので、隙間の中には

- 上のほう … まだ下の一枚が来ていないので、台がのぞく
- そこから下 … **下の一枚の裁ち端**（波）が横切って、その下は下の一枚

が現れる。イラレの図（`生地折り方_02.ai` の1ページ目）にも、
隙間の中だけを走る短い波が描いてあった。それがこの裁ち端である。

生地そのものの端の線は、みみの帯の**外側**に引く。
帯の内側（型紙を置ける面との境）にだけ引くと、隙間の縁がぼやけて穴に見えない。

横わ・上下（`meetH`）も同じ形にしてある。
選べる設定すべてに同じ描き方を出す、という約束にしたがう。

#### みみの札の印は、みみの点々で描く

みみの札には「みみが何枚重なっているか」の印を添えている。
以前はこれを**面の重なりと同じ横棒**で描いていたので、
1枚のときの絵が「生地が一重」の印とまったく同じになっていた
（依頼者の指摘・2026-08-31「これは生地が一重の時の記号と同じです」）。
みみの枚数の話なのか布の重なりの話なのか、読み分けられない。

数え方（棒の数＝枚数）はそのままに、**印だけをみみのものに替えた**。
点々＝みみ、というのは生地の絵でもアイコンでも通してある約束なので、それに合わせる
（`LayoutView.tsx` の `iconSelvageLayers`）。

**太さは図のみみに合わせる。** 帯の太さ・粒の大きさ・粒の間隔を、
生地の絵のみみ（`SEL_BW` ＝ 生地幅の 2.2%、ピッチはその 1.9 倍）と同じ比率にしてある。
最初は細い線に小さな粒で控えめに描いたが、「印だと気づく前に見えない」と言われた
（依頼者の指摘・2026-08-31「耳のマークは細いからか、見えにくいですね。
図の耳の方が太めに描写されていると思うので、この記号も……合わせてみたらどうですか？」）。
印は本物を縮めたものなので、本物と同じ比率で描くほうが小さくても伝わる。

小さく描くとき、ピン穴を破線の丸い端で出すと端の粒が出たり出なかったりして
左右で数が揃わない。札の大きさでは粒そのものを4つ置いている。

#### 下になっている一枚のみみは、少し暗い

生地の面は `CLOTH` と `CLOTH_FOLDED` で上下を描き分けているのに、
みみだけ2枚とも同じ色だったため、重なりの関係がみみのところで途切れていた
（依頼者の指摘・2026-08-30）。

みみの色は `SELVAGE` と `SELVAGE_UNDER` の2組で、
線の色・帯の濃さ・ピン穴の濃さをまとめて持たせてある。
下の一枚は暗い地（`CLOTH_FOLDED`）の上に乗るので、
同じ濃さのままだとかえって薄く見える。線を暗くして濃さも少し上げると、
上下の関係が面と同じようにみみでも読める。

#### 二重は「2枚をずらして重ねた形」で見せる

**生地は上から見た平らな一枚**として描き、二重になっているところは
**同じ大きさの紙を2枚、少しずらして重ねた形**で見せる
（依頼者のイラレの図・2026-08-30。`sheet()` と `under`）。

ずらし方は、折り山の側で2枚がつながっていることから決まる。
そちら側の端はそろえたまま、

- 折り山から**離れる向き**へ `RIM` だけ広げる（みみの側に下の一枚がのぞく）
- 折り山に**沿う向き**へ `UNDER_SHIFT` だけずらす（裁ち端の側に下の一枚がのぞく）

ずらす向きは、縦の折りなら**下**、横の折りなら**右**（依頼者の差しかえ図・生地折り方_02）。
はじめは縦の折りを上へずらしていたが、**台に落ちる影が右下へ出ているので、
ずれの向きと影の向きをそろえたい**という依頼で下向きに変えた。
下の一枚は上の一枚とまったく同じ描き方（波・まっすぐ・回り込み）で描く。
描き分けがそろっていないと、2枚が「同じ布を折っただけのもの」に見えない。

隠れるところは上の一枚が覆ってくれるので、下の一枚のみみも明暗も、
**上の一枚を描く前に**まとめて済ませておけばよい。切り抜きは
`${gid}-clip`（上の一枚）と `${gid}-clip-under`（下の一枚）の2つで足りる。

#### 折り山の端では、2枚の裁ち端が1点に集まって半円になる

**これが無いと「折り返っている」ことが伝わらない**（依頼者の指摘・2026-08-30
「全て『わ』の箇所で折り返して2重になる部分に関して、半円を描くようにして
折り返っている箇所が全く描写されていません」）。ずらして重ねるだけでは
2枚の別の布に見えてしまう。2枚を繋いでいるのは折り山なので、
**ずれた側の折り山の端で、2枚の裁ち端は同じ1点に集まる**。

その点（`leadApex`）を、上の一枚にも下の一枚にも同じ値で渡す。
2本とも折り山の線に**接する向き**でその点を出入りするので、
合わせて半円に見える。これが `turnTo()` と、`sheet()` の中の `corner()`。

寸法は依頼者のイラレの図から実測した（生地幅に対する割合）。

| | 値 | 何の寸法か |
|---|---|---|
| `TURN` | 4.1% | 回り込みが、折り山から離れる向きへ走る長さ |
| `TIP` | 1.9% | 折り山の線が、身頃の裁ち端より先へ出る量 |
| `UNDER_SHIFT` | 5.2% | 下の一枚が折り山に沿ってずれる量 |

折り山の線は `leadApex` から `L - TIP`（横わなら `TIP` から `leadApex`）まで引く。
そこから先は半円で回り込むので、線がそこで終わっていても途切れて見えない。

**折り山は太い筒としては描かない**。以前は折り山を、生地の外へ
`SP` だけふくらませた丸太のような帯として描いていた。
筒が折り山まわりを占めてしまい、**「2枚をずらして重ねた形」のほうが
見えなくなっていた**（依頼者の指摘・2026-08-30）。
折り山はまっすぐな線のまま、端だけを回り込ませる。この2つは両立する。

折った縁がわずかに起き上がって光をひろう感じは、明暗の帯として残してある
（`crestBands`。依頼者の指示「色や陰影はそのまま使いたい」）。
生地の**内側**へ向かって、縁で翳り→白く光り→生地の色へ、と流す。
上の一枚と下の一枚で切り抜きを変えて2回重ねる。

**下の一枚が要るのは、片側から折り切ったときだけではない。**
両側から折って端が中央で出会ったときも、面は丸ごと二重なので下の一枚が要る
（依頼者の指摘・2026-08-30「縦わ・両側について、illustrator で作った図は
下側で生地がずれている描写を入れていたのですが、それがありません」）。
`hasUnder` は `flaps.some((f) => f.full) || meetV || meetH` で見る。
両側わは折り山が2本あってみみの側へ広げる余地がないので、
**折り山に沿ってずらすだけ**（縦わ・両側なら下へ、横わ・上下なら右へ）。
イラレの図（生地折り方_02 の1ページ目・3ページ目）でもそうなっている。

折り山の線は、**ずらして描いた下の一枚の端まで伸ばす**。
2枚を繋いでいるのは折り山なので、上の一枚の端で止めると、
下の一枚がそこから先へ「別の布」のように出ているように見える
（依頼者の指摘・2026-08-30）。

**二重のところも、生地の色は変えない**（依頼者の指示・2026-08-27）。
以前は面の一部だけを覆う折り返しを `CLOTH_FOLDED` で塗っていたため、
「縦わ・片側は明るいのに、縦わ・両側は暗い」という食い違いが出ていた。
二重であることは、ずらして描いた下の一枚・端の線と点々・
「生地が二重」の文字で伝える。
両側から折ってみみが中央で出会う隙間だけは、そこに見えているのが
本当に下の一枚なので `CLOTH_FOLDED` で塗る。

絵についての注意書きは、**絵と同じ枠の中（緑の地の上）に置く**
（依頼者の指示・2026-08-27）。枠の外に出すと画面ぜんぶへの説明に見えて、
どの絵の話なのか分からなくなる。
「型紙の青いふちが縫い代」の一文は、ひとつ前の縫い代付けで済んでいるので置かない。

**「ここで切り分けて、折り方を変える」**（＝区間を増やす）は、
まだ何も置いていないうちは出さず、右寄せの小さな字にしてある
（依頼者の指摘・2026-08-27）。めったに使わないボタンが、
生地の絵と「置くパーツ」のあいだで場所を取っていたため。

折り方は上の1段にまとめてある。折り方のプルダウンの右に、
どこまで折るか（半分に折る／型紙に合わせて）のプルダウンを並べる
（依頼者の指示・2026-08-27）。もとは大きなボタン2つを下の段に置いていたが、
ほとんどの人は「半分に折る」しか使わないので、そのために1段を使わない。

#### 回すのは、左右へ90度ずつの1組にまとめる

**型紙を回す操作は「左へ90°」「右へ90°」の2つのボタンにしてある**
（依頼者の指摘・2026-08-31「任意で左右方向に90°ずつ回転出来るボタンがあれば
それで済むし、分かりやすい」）。まんなかに、いまの角度（0・90・180・270）を出す。

もとは「差し込む（180°）」と「横向き（地の目を変える）」という2つの入り／切りだった。
中身は同じ4通りの向きなのに、目当ての向きにするのにどちらを押せばよいのかが表から読めず、
2つ押して初めて 270 度になる、ということも分からなかった。
名前を実物の言葉（差し込み・地の目）に寄せたぶん、操作としては遠くなっていた。

**言葉のほうは捨てていない。** 角度が持つ意味は、札の下の注意書きで言う。
90度・270度は「地の目が横」、180度は「上下逆（差し込み）」である。
0度のときは何も言わない——ふつうの置き方に注意書きは要らない。

持ちかたは変えていない（`rot90` と `rot180` の2つの真偽値のまま）。
古い見積もりをそのまま開けるようにするためで、
画面に見せる角度は `turnOf` で組み立て、押されたら `turnBy` で組み直す。

##### 回すのは回転であって、鏡ではない（直した）

もとは90度のところで x と y を**入れかえて**いた。入れかえは対角線を軸にした鏡映であって、
回転ではない。枠の大きさは同じなので要尺の数字には出ないが、
左右対称でない型紙は**裏返った形**で描かれていた。
「裏返す」を別の札にして印まで出しているのに、回しただけで黙って裏返るのでは筋が通らない。

`verify:layout` では、多角形の**符号つき面積の符号**で見ている。
回転では符号は変わらず、鏡映では反転する。
左下を欠いた五角形を、90度・180度・270度・裏返しの4通りで通して、
裏返しのときだけ符号が反転することを確かめている。

##### 向きのある生地の 180 度は、止めずに知らせる

もとは「向きあり」の生地では「差し込む（180°）」の札を灰色にして押せなくしていた。
左右へ90度ずつ回す作りにした以上、**途中の180度だけ通さない、という作りにはできない**。
そこで、止めるのをやめて注意書きに変えてある
（「実物でありうることは止めない」という約束事のとおり・依頼者の指示・2026-08-30）。

あわせて、知らせる条件を `rot180` から `turnOf(p) === 180` に直した。
270 度も `rot180` が立っているが、これは「地の目が横」の側であって差し込みではない。
`rot180` だけで見ていると、右へ3回まわしただけの型紙に「上下逆です」と出る。

#### 二本指でひろげる・つまむ

生地は幅110cm・丈2mといった大きさで、それを電話の画面に丸ごと収めている。
1cm きざみで型紙を突き合わせたいのに、画面の上では 1cm が3画素にもならない。
指で置くには、寄って見られる必要がある——というのが依頼者の指摘（2026-08-31）。

**枠そのものは変えず、見る窓（`viewBox`）だけを動かしている。**
図の大きさも、指の動きを実寸に直す換算（`mmPerPx`）も、すべてこの窓から出しているので、
寄ったまま型紙を引きずっても指と型紙はずれない。
実測でも、同じ画素ぶん引いたときの動きが 1倍で 70mm、3倍で 20mm と、きれいに 1/3 になる。

窓は図の外へは出られないようにしてある。迷子になると戻る道が
「もとの大きさへ」しかなくなるため。上限は6倍。
110cm 幅の生地が電話の画面で 18cm ぶんになる大きさで、
これ以上寄れても、どこを見ているのか分からなくなるだけ。

指の受け方は、触れている指の数で決めている。

- 一本だけで、つかんだ先が型紙 → これまでどおり型紙が動く
- 一本だけで、つかんだ先が生地 → 図そのものがずれる
- 二本目が触れた瞬間 → 型紙を動かすのはやめて、ひろげる・つまむに移る

寄っているあいだは、図の右上に「2.3倍 ／ もとの大きさへ」と出る。
倍率を書いてあるのは、寄っていることに気づかないまま
「型紙が大きくなった」と誤解されないようにするため。

##### 名前と印は、寄っても同じ大きさのまま

型紙の枠・地の目線・折り山の線は、生地の上に**実際にある**ものなので、
寄れば大きくなってよい。いっぽう型紙の名前や「地の目が横」「×2」といった印は、
読むために添えてあるだけで、生地の上にある物ではない。
いっしょに大きくすると、寄って合わせようとしている当の型紙を、名前が覆いかくしてしまう。

そこで、名前と印だけは倍率で割ってある（`lbl()` と、
[src/components/PatternMarks.tsx](src/components/PatternMarks.tsx) の `fontShrink`）。
画面の上での大きさが、寄っても変わらない。

#### ふつうと違う置き方は、その型紙の上で言う

回転・反転はいつでも自由にできる。**ふつうと違う置き方をしたときに止めるのではなく、
そうなっていることを型紙の上に書く**（依頼者の指示・2026-08-30）。

型紙は本来、地の目を縦に通して置く。ところがサーキュラースカートのように
生地の幅に縦地で入りきらないものがあり、そのときは横地で裁つことが実際にある。
だから「できません」と選択肢から外さず、
「地の目が横」と型紙の左上に印を出し、下のメニューにも理由を添えて書く。
色は赤（`seam`）ではなく落ち着いた茶（`#8a6a2e`）。誤りではないので、
誤りの色を使わない。

印は型紙の**左上の角**に、左そろえで積む（「地の目が横」「裏返し」の2つが
同時に付くことがある）。型紙の名前と地の目線は真ん中にあるので、
真ん中へ書くと重なって読めない。印があるぶんだけ、名前は下へどける
（`PatternMarks` の `labelShift`）。1つで2枚とれる印（×2）は、
名前とぶつからないように**右下の角**へ置いてある。

#### 取り込んだ大きさを、選んだときの板の中で見せる

**型紙が実物の何センチとして入っているかを、確かめられるようにしてある**
（依頼者の指示・2026-08-31「きちんと寸法が合っているもので取り込まれているということを
確認できる安心材料として、数値が見られた方がいい」）。

定規の読み取りが少しでもずれていると、取り込んだ型紙は本物より大きいか小さいかになる。
それに気づかないまま並べても、出た要尺には意味がない。
写真から起こしている以上、ここは学生が目で突き合わせられるようにしておくところである。

出すのは選んだときの板の中だけで、**型紙の上には出しっぱなしにしない**（同じ指示）。
図の上は型紙のためにあけておきたいのと、ふだんは見なくていい数字だからである。

2つ並べている。実物に定規を当てて比べられるのは前者のほう。

- **型紙** … 出来上がり線の大きさ。取り込んだときの `widthMm` / `heightMm` そのもの
- **裁ち切り** … 縫い代まで入れて、生地の上で場所を取る大きさ（`cutSizeOf`）

向きは型紙自身のもの（地の目が縦）で書く。生地の上で横向きに置いても数字は入れかえない。
実物を机に置いて測るときの向きと同じにしておきたいため。

#### 選んだ型紙のメニューは、出たことが分かるように

画面の下端に出る操作メニューは、背景が白いだけだと出たことに気づけない
（依頼者の指摘・2026-08-30）。下からすっと立ち上がる動き（`panel-up`）を付け、
上の縁を「わ」と同じ緑の太線にし、影を濃くし、つまみの横棒を置いてある。
型紙を選び直すたびに出しなおすため、`<Controls key={selected.id}>` にしてある。
動きを減らす設定の人には、動きだけ出さない（`prefers-reduced-motion`）。

ただし、それだけでは足りなかった。動きと縁を付けたあとも
「特にアニメーション的な動きはなく、いつも通り白い枠で出てきています」と言われている。
動き自体は出ていた（計算後の `animation-name` は `panel-up`）。
効いていなかったのは**地の色**のほうで、画面の地（`--color-chalk`）が
ほとんど白なので、白い板を白い紙の上に置いていたことになる。

**メニューの地を薄い緑（`--color-mat-50`）にする。**
色は動きと違い、見た瞬間からずっとそこにある。動きは0.34秒で終わる。

地に色を付けたら、その上に乗るものの色も一緒に決め直す
（依頼者の指摘「背景色を付けるとすると、現在のボタンや文字の背景色が
必要か不要か、その辺も考える必要がある」）。

- 押していないボタンは**白地**にする。緑の板に載せた札に見える。
  地と同じ色のまま枠線だけだと、押せるものだと分からない
- 「この1つで◯枚」の札も白地にする。もとは薄い緑だったので板と同じ色になる
- 「あとで裁つぶん」の札は生成り（`hold-50`）のままでよい。緑の上でむしろ目立つ
- つまみの横棒は薄い緑の上では見えないので、一段濃い緑（`mat-300`）にする
- 説明文（`Note`）は地の色を持たないので、そのまま

#### 横わでも「きっちり半分に折る」を選べる

**どの折り方でも選べる**（依頼者の指示・2026-08-30
「横わもその状態だと不自然なのと2重になっていることが伝わりにくいと思うので、
illustrator のようにして下さい」→「両方を選べるようにする」）。
以前は縦わだけに限っていた。横わは「半分の元になる長さ」をこれから求めるところなので、
きっちり折りようがない、と考えていたためである。
その結果、横わは折り山の線が1本引いてあるだけの一重の図になり、
折ったことも二重になったことも伝わらなかった。

意味が縦と横で違うので、そこだけ押さえておく。

- **縦わをきっちり折ると、置ける幅が半分になる**（有効幅 → その半分）。
  買う長さは変わらない
- **横わをきっちり折ると、買う長さが倍になる**（面の長さ → その倍）。
  置ける幅は変わらない

実装で1つだけ順番の縛りがある。横わの折り込む深さは**面の長さから決まる**ので、
`computeYardage()` では**面の長さを先に出してから深さを決める**
（[src/lib/fabric.ts](src/lib/fabric.ts) の手順1と手順2）。
要尺は元から `surfaceLength + depth.top + depth.bottom` で出しているので、
深さが面の長さと等しくなれば、そのまま倍になる。
片側だけの横わ（`hTop` / `hBottom`）は深さが面の長さそのもの。
上下の両側（`hBoth`）は合計が面の長さで、内訳は当てた型紙が決める（後述の `share()`）。

図のうえでは1か所だけ手を入れている。まだ何も置いていないと面の長さが 0 で、
折ったはずの図が一重のまま出てしまう。空の生地にも折り目が要るので、
描いてある高さを折った形で見せる（`LayoutView.tsx` の `depth`）。計算には効かない。

#### 端どうしが出会うところの上には、型紙を置けない

**両側から折って端どうしが出会うところ（出会い目）をまたいで型紙は置けない**
（依頼者の指摘・2026-08-30「間の隙間が空いているところの上には
型紙は載せられないはずです」）。以前は置けてしまううえ、
面が丸ごと二重だからという理由で**「1つで2枚」と数えてさえいた**。

そこがなぜ置けないかというと、面としては丈ごと二重でも、
**上になっている一枚はそこで切れている**から。
上から折り返してきた一枚と下から折り返してきた一枚は別々の布で、
真ん中で突き合わせているだけである。またいで裁つと、
下の一枚からは1枚とれても、上の一枚は2つに割れて使えない。

`computeYardage()` は出会い目の座標（`meetX` / `meetY`）を出し、
またいだ置き方に `acrossMeet` の知らせを出す。枚数も 1 に落とす。

なお `doubled`（二重の帯）は「布が二重かどうか」だけを言う配列なので、
出会うときは面丸ごと1本のままにしてある。
またげるかどうかは別の話として `meetX` / `meetY` が持つ。

**知らせを出すだけでは足りない。引きずっている最中から越えられないようにする**
（依頼者の指示・2026-08-30「隙間が空いている部分の上には乗せられないようにしてください」）。
`LayoutView.tsx` の `keepOffMeet()` が、指の行き先が出会い目をまたぐときに
はみ出しの少ないほうの側へ寄せる。そちらに入らなければ反対側へ。
どちらにも入らない大きさのときだけ、そのままにして `acrossMeet` の知らせに任せる。

ここは、ふだんの「ダメとは言わず注意書きで知らせる」という方針の**例外**である。
地の目が横になる・縫い代がぎりぎりといった話は実物でもありうることなので注意書きで済ませるが、
出会い目をまたぐのは実物では**そもそも起こりようがない**（上の一枚がそこで切れている）。
起こりようのないことを、手で作れてしまってはいけない。

#### 折り返す深さは、当てた型紙に合わせて動く

**「両端が出会うまで折る」を選んでも、折り返しの深さを半分ずつに決め打ちしない**
（依頼者の指示・2026-08-30「その輪の位置、要は折り返ってきて2枚が重なっている幅を
自動で調整できるようにしなければならないと思います」）。

実物の手つきがそうなっている。人は「まず半分に折ってから型紙を置く」のではなく、
**「この型紙が入るところまで折る」**という順に手を動かす。
折り山に丈 27cm の型紙を当てたなら、その側の折り返しは 27cm 深くなる。

したがって決まっているのは**合計**だけで（縦わなら有効幅の半分、横わなら面の長さ）、
内訳は当てた型紙が決める。`computeYardage()` の `share()` がこれをやっている。
どちらの折り山にも何も当てていないときだけ、半分ずつに分ける
（空の生地でも折り目が見えている必要があるため）。

これで、以前に出ていた不具合も消えた。以前は深さを面の半分に固定していたので、
折り山に当てた型紙が**必ず**出会い目をまたぎ、置いたそばから知らせが出ていた。

札の名前も**「中央まで折る」から「両端が出会うまで折る」**に変えた。
出会うところは、もう真ん中とはかぎらないため
（`FoldPicker.tsx` と `LayoutView.tsx` の両方）。

#### 効いていない折り山があれば、そう伝える

両側から折ったのに片側にしか型紙を当てていないと、
**反対側は折らなくても結果が同じ**になる。これは依頼者自身が予想していたことでもある
（2026-08-30「結局上側の輪の部分だけを使っていった場合、下輪にはなっているものの、
下輪の意味がなくなってきてしまうというケースがあるのかなとは思っています」）。

黙って同じ数字を出すと、学生は折り方の選択が効いていると思ったまま進んでしまう。
`LayoutView.tsx` の `idleFold` が、選んだ2本のうち深さが 0 のほうを見つけて、
絵の下にそう書く。禁止はしない——折り方として間違っているわけではないので。

生地の折り方は、平面図と断面図の2枚で同じことを言っている。
両側から折って**みみが中央で出会うとき**は、そこにわずかな隙間を空けて描く
（依頼者の指示・2026-08-27）。突き合わせて描くと二重の帯が1枚の面につながって見え、
そこが端どうしの出会うところだと分からなくなるため。絵のうえだけの隙間で、計算には効かない。

帯の名前は「二重」ではなく**「生地が二重」**と書く。
主語がないと、置いた型紙が2枚という意味に読めてしまうため（依頼者から実際にそう質問された）。
帯が細くて字がはみ出すときだけ短いほうに落とす。

#### 帯の札は、帯のはじまりへ寄せる

**帯のまんなかには置かない**（依頼者の指摘・2026-08-31「横わのとき、札と型紙の名前が
重なって読めない」）。帯のまんなかは、置いた型紙の名前と地の目線が必ず通るところだからである。

- 縦の帯（左右の折り返し）は上下に長いので、**上端**へ寄せる
- 横の帯（上下の折り返し）は左右に長いので、**左端**へ寄せる。
  さらに上下も、帯のまんなかではなく**折り山ぎわ**へ逃がす。
  横の帯の高さは当てた型紙の丈そのものなので、帯のまんなかは型紙のまんなかであり、
  そこには名前と、横に寝た地の目の矢が重なって通っている
- 面が丸ごと二重のときだけは、折り山ぎわではなく上端に置く。
  このとき帯は生地そのものなので、どこに置いても言っていることは変わらない

「ここまで◯ cm」は線の**下**に置く。以前は文字の足を線に合わせていたので、
字のほとんどが線の上——型紙の側——にはみ出し、いちばん下の型紙の裾と重なっていた。
残りが浅いときは、その帯に収まるところまで戻す。

#### 下に折り山があるときは、そこが生地の下端

図に描く生地の長さ `L` は、まだ何も置いていなくても生地に見えるように、
ふだんは少しだけ長め（40cm）に描く。
けれど**下の辺が折り山のときだけは、使っている長さがそのまま下端**になる。
折り山は「そこで生地が折り返っている場所」なので、その先に生地は無い。
長めに描くと、下の折り山に当てたはずの型紙が折り山から 13cm ほど浮いて見えていた。
計算（`computeYardage`）のほうは最初から正しく、絵だけがずれていた。

#### 横わの断面では、両端は「みみ」ではなく「裁ち端」

断面図（`FoldDiagram.tsx`）は、縦わなら**幅の向き**に切った形なので両端はみみだが、
横わは**長さの向き**に切った形なので、両端ははさみで切った裁ち端である。
みみはこの断面では奥行きの方向にあり、絵には出てこない。
同じ絵を向きだけ変えて使い回していたので、横わのときも端を「みみ」と呼んでいた
（依頼者の指摘・2026-08-31）。

絵の下のひと言（`Hint` の見出し）は、**折り方の名前ではなく、いま描いてある絵**を見て決める。
「両端が出会うまで折る」を選んでいても、当てた型紙が浅ければ折り返しは面を覆いきらず、
絵には一重のところが残る。そこで「ぜんぶ二重」と書くと、絵と文が食い違う。
判定には `hasUnder`（どこかの折り返しが面を覆いきっている、または出会い目ができている）を使う。

**裏返して置いた型紙**は、白い表ではなく、うっすら斜線の入った「紙の裏」の色で描き、
「裏返し」と書き添える（依頼者の指示・2026-08-27）。形だけでは裏返したことに気づけない。

絵は全部、裁縫室にある物を横から見た形で描いてある（横棒1本＝一重、横棒2本＝二重、
ヘアピン形＝折り山、はさみ＝裁ち端、点々＝みみ）。歯車やフォルダのようなパソコンの記号と、
絵文字は使っていない。詳しくは `Icon.tsx` の先頭に書いてある。

外部の画像処理ライブラリ（OpenCV.js など）は使っていない。
読み込みが10MB近くなり、教室のWi-Fiで一斉に開くと初回が重くなるため。
必要な処理は上記のとおり自前で書いてある。

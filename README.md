# 要尺シミュレーター

服飾学校の学生が、緑のマットの上で撮った型紙の写真から、生地の必要用尺を確かめるためのWebアプリ。

撮る → 定規を合わせる → 実寸を見る → パーツを貯める → 縫い代を付ける → 生地に並べて買う長さを出す、
まで通しで動く。

写真の処理も要尺の計算も、すべてブラウザの中だけで行う。
**写真も型紙の形も、この端末から外へ出ない。** サーバーは無い。

## 動かす

```
npm install        # 最初の1回だけ
npm run dev        # http://localhost:5173 が開く
```

同じWi-Fiのスマホからも見たいときは `npm run dev -- --host` にする。
ただしそのやり方は開発中の確認用で、日常づかいには向かない
（毎回このパソコンを起動して、同じネットワークにいる必要がある）。
学生に配るのは下の「配る」のほう。

## 確かめる

```
npm run verify         # 写真から実寸に戻せるかを、合成画像で検算する
npm run verify:layout  # 縫い代・わ・区間・要尺の計算を検算する
npm run sample         # 動作確認用の写真 ../テスト用の写真.png を作り直す
npm run seed           # 開発用の「撮影ずみ」データを作り直す（下記）
```

### 撮影を飛ばして、縫い代や配置の画面だけ触る

URL のうしろに **`?dev`** を付けて開くと、最初の画面に開発用の口が出る。
入るのは前スカート・後ろスカート・ベルトの3点で、
**どこから始めるか**を3つから選べる（依頼者の指示・2026-08-27）。

- **パーツの一覧から** … 取り込んだ直後の状態
- **縫い代から** … 1枚目の縫い代の画面を開いた状態。縫い代の画面だけ見たいとき
- **並べるところから** … 生地の上に並べる画面

縫い代は既定値が入った状態で入るので、そのままでも並べるところまで進める。

中身は依頼者がイラストレーターで作ったスカートの図を、
**アプリとまったく同じ処理にかけて**取り出した実寸の輪郭（[src/lib/devSeed.ts](src/lib/devSeed.ts)）。
手で作った都合のいい形ではないので、実写に近い粗さのまま入っている。
図では前後スカートの定規が縦、ベルトの定規が横に置かれていて地の目の向きが違うため、
2回に分けて読んでいる（実際の撮影でも、向きの違うものは分けて撮ってもらう）。

一度 `?dev` で開いたら、そのあとは付けなくても出る（端末に覚えさせてある）。
スマホでホーム画面に登録したり「読み込み直す」を押したりすると `?dev` が落ちてしまい、
そのたびに URL を打ち直すことになるため。`?dev=0` で消える。

`?dev` を一度も付けていない学生の URL には、この口は出てこない。

データ（[src/lib/devSeed.ts](src/lib/devSeed.ts)）は、はじめは押したときに
別ファイルとして読みに行っていたが、**いまは本体に入れてある**。
置きなおすたびにファイル名が変わるので、古いページを開いたままの端末では
その名前のファイルがもう無く、押しても読み込めなくなっていた（実機で2度起きた）。
本体に入っていれば、どの版を開いていても必ずある。増えるのは 0.5kB 弱で、
配信の重さには関わらない。

`npm run verify` は、実寸が分かっている型紙をわざと斜めから撮ったように歪ませた画像を作り、
アプリの処理で元の寸法に戻せるかを見る。定規の自動判別についても、
傾き0〜35度・距離60〜160cm を総当たりして「外れた提案を出さないこと」を確かめている。

**4隅が指のぶんずれても持ちこたえるか**も、ここで見ている。
写真から実寸に直す変換は、もとは射影変換（4点をぴったり通すもの）だった。
4隅が正確なら誤差ゼロだが、指で合わせると数画素ずれ、
そのずれを「そういう遠近だった」と受け取って、定規から遠い型紙ほど大きく歪ませる。
合成画像では ±8画素のずれで最悪56%も狂った。
いまは相似変換（回転＋一様な拡大）を既定にしてあり、同じ条件で最悪2%に収まる。
検算はこの2つを並べて表示し、相似のほうが強いことを毎回確かめている。

定規1本で何枚も一度に撮る場合も、ここで確かめている。
定規は写真の**面そのもの**の実寸を決めているので、写真に1本あれば、
そこに写っているパーツは全部そのまま測れる（定規を緑の上に置いた場合と、
どれか1枚に載せた場合の両方を検算してある）。
ただし地の目の向きも同じ定規から取っているため、
**一度に撮るパーツは地の目を全部そろえて定規と平行に**置く必要がある。
この2点は撮影の画面にも書いてある。

`npm run verify:layout` は写真を使わない。実寸の輪郭から先だけを見る。
いちばん大事なのは最後の節で、**学校の配布資料に載っている目安と突き合わせている**。
マーメイドスカート③の目安【上パーツ丈+6〜10】＋【（下パーツ丈+20）×2】に対し、
同じ条件でアプリの計算が 156cm を出すことを確かめている（目安は 154〜158cm）。
自分で作った数字どうしを比べても正しさの証明にはならないので、外から来た数字と合わせている。

## 配る

学生に伝えるURLは、これひとつ。

**https://junnosuke0923.github.io/yojaku/**

置きなおすときは：

```
npm run deploy     # 検算 → ビルド → GitHub へ送る、までまとめて行う
```

検算（`verify:layout`）が落ちたらそこで止まるので、計算が壊れたまま配ることはない。
送り先は `gh-pages` ブランチで、GitHub Pages はそこを見ている（[scripts/deploy.mjs](scripts/deploy.mjs)）。

GitHub Actions（GitHub 側で自動ビルドするしくみ）は使っていない。
それには `workflow` という追加の権限が要るが、
使う端末の `gh` のログイン状態がそこまで整っていなかったため、
手元でビルドして送るこの形にした。結果は同じで、手順はこちらのほうが短い。

### 置きなおすと、古いページを開いたままの端末が壊れる（対処ずみ）

置きなおすたびに JS のファイル名が変わる（中身で名前を決めているため）。
GitHub Pages は index.html を10分ぶんキャッシュさせるので、
**スマホが古い index.html を持ったままだと、そこに書いてある名前のファイルはもうサーバーに無い。**
症状は「押しても何も起きない」「読み込みに失敗しました」で、
2026-08-27 に実機で実際に起きた（`?dev` の「撮影ずみのパーツを入れる」が失敗した）。

そのため、ビルドの日時を2か所に置いてある。

- アプリの中（`__BUILD_ID__`、`vite.config.ts` の `define`）
- `version.txt` という一行のファイル（同じく `vite.config.ts` で書き出す）

アプリは開いたとき・画面に戻ったとき・5分おきに `version.txt` を
`cache: 'no-store'` で見にいき、自分の目印と違えば
「新しい版が出ています／読み込み直す」と出す。黙って読み込み直すことはしない
（作業中に指の動きを取り上げられると困るため）。取り込んだパーツは端末に残るので、
読み込み直しても消えない。

**「読み込み直す」は、ただのリロードではない。**
リロードでは、端末や途中の配信網が持っている古い index.html がそのまま出てくることがある
（実際にそうなった）。URL のうしろに毎回違う印（`?v=…`）を付けて開き直すことで、
同じ住所と見なされないようにしてある。印は開いたあと、履歴から消しておく。

version.txt が無い配信（開発中のサーバーや、Wi-Fi のログイン画面）は
index.html を代わりに返してくることがあるので、
**日時の一行に見えない返事は無かったことにする**。

送る前に手元で確かめたいときは：

```
npm run build      # dist/ フォルダができる
npm run preview    # できた dist/ をそのまま開いて確かめる
```

参照はすべて相対パスにしてあるので、URLにリポジトリ名の階層が付く GitHub Pages でも、
階層の付かない Cloudflare Pages でも、同じ `dist/` がそのまま動く。

スマホのカメラは `https` のページからでないと使えないため、この配り方が前提。

  contour.ts      輪郭のなぞり（Moore近傍追跡）

  homography.ts   射影変換。斜め撮影の歪みを打ち消す

  CornerPicker.tsx  定規の位置を教えてもらう。長方形のまま動かす／回す／伸ばす
  RulerToggle.tsx   50cm / 30cm の選択

### 「わ」の決め方（[src/components/FoldPicker.tsx](src/components/FoldPicker.tsx)）

もとはプルダウンで「縦わ・片側」などの**名前**から選ばせていた。
その名前は、頭の中でいったん図に直さないと選べない。
いまは生地を上から見た小さな図が出ていて、**その辺そのものを押す**
（依頼者の指示・2026-08-28）。教科書の裁ち合わせ図に添えてある折り図と同じ形なので、
学生が学校で見ているものと一致する。

押す口をこの小さな図に集めてあるのは、大きい裁ち合わせ図が
**型紙を指で引きずる場所**だから。そこに「押すと生地の構造が変わる」仕掛けを混ぜると、
型紙を動かすつもりの指が折り方を変えてしまい、並べたものが総崩れになる。
それに生地は縦に長く、下端は画面の外にあることが多い。この小さな図なら4辺とも常に見える。
ただし大きい図の**外側にある札**（「わ 折り山」「みみ」）だけは押せる。
そこは型紙と重ならない余白なので、指が迷い込む心配がない。第二の入口になっている。

さわり方は2通り。**押す**と「わ」が付いたり外れたりする。
**辺をつまんで内側へ引きずる**と、引いた深さで折る深さまで決まる
（浅ければ「型紙に合わせて」、きっちり折り切る位置の 76% まで行くとそこに吸い付く）。
引きずるほうは押すことの上位互換ではなく、「半分に折る」の選択を
ひとつの動作にまとめるためのもの。プルダウンも残してある。

#### この図が描いているのは、折りたたんだあとの面

折り山が**辺のところに来ている**のがその印である。開いた生地なら折り山は真ん中に来る。
ここを取り違えると「半分」の意味が変わってしまうので、はっきりさせておく
（依頼者の指摘・2026-08-28）。

- **片側だけ折るなら、折り返した一枚は向かい側の生地端まで行く。**
  縦わならみみからみみへ折るのだから、動いたみみは向かい側のみみの上に重なる。
  **横わも同じ**で、動いた裁ち端が向かい側の裁ち端の上に重なる
  （依頼者の指摘・2026-08-28）。落ち着いた図では、縦わのときその辺に
  点々が2本並ぶ（みみが2枚あることを表す）
- **両側から折るなら真ん中まで。** 左右（上下）の端が中央で出会う

折れる動きも、引きずったときの吸い付き先も、この位置に揃えてある（`snugDepth`）。
動く一枚の先頭も、動いている当のものを描く——縦わならみみ（点々）、
横わなら裁ち端（波）。落ち着いたあとの辺の描き方と揃っていないと、同じ端に見えない。

余白の取り方はこの決まりから出てくる。折る前の一枚は生地の外側に開いて寝ているので、
折る向きにその大きさぶんの余白が要る。

- **幅の向きには取ってある**（余白 46 に対し生地の幅 40）。
  左右の端はみみ＝布の実在の端で、そこから先に布は無い。
  無いはずのものが図の外へ続いているように見えてはいけない
- **丈の向きには取っていない**（余白 32 に対し生地の丈 56）。
  横わで折り始めるとき、開いた一枚は図の上下からはみ出して切れる。
  布は長く続くものなので、その向きに図が足りていないのは嘘ではない。
  ここまで余白を取ると図が小さくなりすぎ、余白ばかりの札になってしまう。
  大事なのはどこへ着地するかで、そこは必ず図の中にある

**片わは上下左右どの辺でも作れる**（依頼者の指示・2026-08-28）。
前中心が「わ」で後ろ中心はそうでない、という場面は実際にある。
そのとき現実では右側を山折りにして、そこに前中心を当てる。
左を「わ」にして型紙を裏返しても布としては同じものが取れるが、
このアプリは**実際の裁断の下稽古**でもあるので、現場で踏む手順のほうを採る。
そのため折り方には `vRight`（縦わ・右）がある。
折りのしくみは初めから「どの辺か」で動いていた（`foldSidesOf` が辺の組を返す）ので、
断面図も大きい裁ち合わせ図も、手を入れずにそのまま右側に対応した。

#### 折れる動き

辺を押して「わ」が付いた瞬間だけ、外に開いていた一枚が
折り山を軸に**起き上がって内側へ倒れてくる**。

ここは一度やり直している。初めは 260ms で、線だけの一枚を裏返していた。
それでは「折れる動作というのが見て取れない」（依頼者・2026-08-28）。
直したのは3つ。

- **760ms** に伸ばした。倒れるのに7割を使い、倒れ切ったところでいったん止めてから消える。
  止める間があると、そこが「折り終わったところ」だと分かる
- **生地と同じ色で塗り、下に影を落とす。** 色を変えれば目立つが、
  どの折り方でも生地の色は変えない決まりがある（依頼者の指示・2026-08-27）。
  そこで色ではなく影で浮かせた。影は動いている間だけで、落ち着いた図には残らない
- **途中の姿**を挟んだ。裏返すだけでは、線が横に滑ったようにしか見えない。
  折っている途中の紙は立ち上がってこちらに近づくので、途中では軸の向きに潰しつつ
  軸と直角の向きには少し大きくし、わずかに持ち上げる（`flipFrames` の `mid`）

引きずって折ったときは動かさない。指がもう動かしたあとなので、重ねる意味がない。
動きを控えめにする設定の端末では、動かさずに結果だけ出る。

ベルトや見返しのように、仮縫いのあとで寸法が変わるものは、
最初の裁断では布を裁たずに場所だけ空けておくことが多い（依頼者の指示）。
そのため「生地の上に並べる」画面には、型紙とは別に
**後で裁つぶんの余白**を置ける口がある。
写真も出来上がり線も持たない、指定された寸法どおりの長方形で、
斜線と破線で「まだ手を付けていない場所」として描き分ける。
場所は取るので、買う長さにはきちんと効く。

画面のいちばん上の**段階の帯は、前へも後ろへも通れる道**である
（依頼者の指示・2026-08-27）。押せるかどうかを決めるのは
「その段階で見せるものが、もう揃っているか」だけで（`App.tsx` の `canGo`）、
揃っていれば行ったり来たりできる。
写真も定規もまだ、という段階は、行っても何も無いので押せないままにしてある。

**先へ進むほうも押せる**ようにしたのは、依頼者の指示による。
たとえば並べている途中で、縫い代を一本だけ直してまた続きへ戻る——
という往復ができないと、直すたびに前の画面をひとつずつたどり直すことになる。
取り込んだものも並べたものも `parts` にまとめて持たせて端末に残してあるので、
画面を行き来しても、直したところは直ったまま戻ってくる。
縫い代を広げれば、並べる画面の型紙もその場で広がる。

帯の上の細い線は3通りに塗り分ける。
濃い緑＝ここまで来た、薄い緑＝押せば行ける、灰色＝まだ行けない。

取り込んだパーツと生地の設定は端末の中に残るので、閉じても次に開けば続きから触れる。
そのぶん、次の課題に移るときや人に渡して試してもらうときに戻せないと困るため、
見出しの右に**「はじめから」**を置いてある（依頼者の指示・2026-08-27）。
消すと戻せないので、何がいくつ消えるのかを示して一度たずねてから消す。

このボタンが消すのは、**いま出ている画面のぶんだけ**（依頼者の指示・2026-08-27）。
並べる画面で押したときは、並べた場所だけを置く前に戻し、
取り込んだパーツも生地の設定もそのまま残す。
以前はどの画面から押しても全部消していたため、
「置きなおしたいだけ」で押した結果、撮るところからやり直しになった。
たずねる文面も、その画面で実際に消えるものと残るものを書き分けてある。

ここで出るのは**概算**である、と2か所に書いてある（依頼者の指示・2026-08-28）。
撮る前の画面のいちばん上と、買ってくる長さが出たすぐ下。
数字を見てから初めて知るのでは遅いので、始まりにも置いてある。
型紙の形は写真から読み取っているので実物とは数ミリの差が出るし、
地直しの縮みや柄合わせ、裁つときのくせでも変わる。
ひと言だけ出して、理由は「？」の中に畳んである。

買ってくる長さは、並べる画面の**いちばん下**に置いてある（依頼者の指示・2026-08-27）。
上にあると、まだ何も並べていないうちから結果が目に入って、
「並べる → 長さが出る」という順に読めない。
「置くパーツ」のすぐ下なので、1つ置いて目を下ろせば、そのたびに変わるのが見える。

出した見積もりは、名前を付けて**しまっておける**（依頼者の指示・2026-08-28）。
しまうのは結果の数字だけではなく**作業まるごと**——
型紙・縫い代・生地の設定・並べ方まで（依頼者の選択）。
数字だけにすると、あとで見て直したくなったときに何もできない。
まるごと持たせておいて、一覧に出すぶん（買う長さ・生地幅・日付）だけを
`summary` に取り出してある。

置き場所は**この端末の中だけ**（依頼者の選択）。
ファイルにも画像にも書き出さない。学校の管理端末で使うものなので、
写真から取った型紙の形も、この端末から出ない。

しまう口は並べる画面の下（買う長さのすぐ後ろ）、開く口は撮る画面。
撮るボタンより下に置いてある。ふだんの入口は「撮る」なので、
上に積むと毎回それをまたぐことになる。ふだんは最近の3件だけ出す。

同じ名前でしまうと**書きかわる**。名前がそのまま行き先になるので、
「同じ名前＝同じもの」と読めるほうが分かりやすく、
「新しくしまう」のか「上書きする」のかを学生に考えさせずに済む。
開いたものは名前の欄に名前が入った状態で戻ってくるので、
直してもう一度しまえば、増やさずにその場で書きかわる。

しまえる数は20件まで（`MAX_SAVES`）。1件に型紙の輪郭がまるごと入るため、
際限なく増やすとブラウザの置き場所が尽きる。
尽きたときに黙って消えるのがいちばん困るので、先に上限で止めて知らせる。
座標は 0.1 mm きざみに丸めてからしまう。それより細かい桁は裁つときに意味を持たないのに、
置き場所だけはその桁のぶんきっちり食う。

開くと、いま触っているぶんは置きかわる。戻せない操作ではない（下の控えに積まれる）が、
黙って置きかえると何が起きたのか分からないので、作業中は一度たずねる。
消すほうは戻せないので、必ずその行の中でたずねてから消す。

作業中はいつでも **1つ戻る／1つ進む**が使える（依頼者の指示・2026-08-27）。
見出しの右、「はじめから」の隣にある。
戻せるのは取り込んだパーツ・縫い代・生地の設定・並べた位置で、
つまり画面をまたいで戻る（縫い代を付けたあと並べる画面へ進んでも、縫い代まで戻れる）。

しくみは単純で、**変わるたびに全部の控えを1つ取っておく**だけ。
どの画面も `updateParts` という一箇所を通るので、画面ごとの書き分けが要らない。
控えは40回ぶんで、古いほうから捨てる。

型紙を指で引きずっているあいだは、途中の位置をいちいち控えない。
1回の引きずりに**合図（`drag1`, `drag2`, …）を付けて**、同じ合図が続くあいだは
控えを積み増さないようにしてある。はじめは「前の変化から◯ミリ秒以内なら同じ操作」と
時間で見ていたが、生地を長くすると1回の描き直しに1秒近くかかることがあり、
そのやり方では毎回まとめ損ねた（実測で8回の移動が7.9秒）。時間に頼らない形にしてある。

## 画面の文章について

説明は**既定で短く**する（依頼者の指示・2026-08-27。
「説明文がやたら長かったり多かったりして、あまり感覚的にやれない」）。

常に出しておくのは、それだけで意味が通るひと言だけにして、
理由や例外は「？」の中に畳む（`Icon.tsx` の `Hint`）。
情報は減らさず、**見えている量だけを減らす**。分からなくなった人の逃げ道は残す。
畳んだ説明を開く的は行そのものなので、小さな「？」印を狙う必要はない。

図の下に長い文を置かないことも同じ理由。絵より先に文を読ませてしまう。
断面図の下にあった一文は落とした（依頼者の指示・2026-08-27）。
「二重」「一重」「わ」「みみ」は絵の中に書いてあり、同じことを文でもう一度言っていた。
まだ折っていないときだけは、何をすれば折れるのかを短く添える。

**同じ絵をいくつも並べない**（依頼者の指摘・2026-08-27。
「縫い代を示したピクトグラムが同じものがそこら中にある」）。
絵は、あるだけでその場所の意味を言うものなので、
同じ絵が1画面に3つあると、どれも意味を持たなくなる。
縫い代の画面では、はさみ・縫い代の絵を、見出しの1つに絞ってある
（補足の行は「？」の印、「まとめて」の行は文字だけ）。

同じ理由で、**同じ絵に二通りの意味を持たせない**。
「しまっておく」にはしおりの絵（`save`）を新しく足してある。
並べる画面には「後で裁つぶんの余白（`hold`）」が先にいるので、
そこで絵を使い回すと、ひとつの画面で同じ絵が二つのことを指してしまう。

この方針に直したときの文字数は、撮る 307→156、パーツ 556→396、並べる 777→448。

### はじめて開いたときの案内（[src/components/Tour.tsx](src/components/Tour.tsx)）

**いまは止めてある**（`TOUR_ON = false`。依頼者の指示・2026-08-27）。
機能の直しと画面の調整がこの先も続くあいだは、案内の文面と実物が食い違いやすく、
画面を変えるたびに文面も直すことになるため。画面が固まってから出す。
仕組みそのものは動く状態で残してあるので、`TOUR_ON` を `true` にすれば戻る。
そのときは、案内と同じことを言っている常設の説明（パーツ一覧の
「枚数はできあがりに必要な数」）を、もう一度消すこと。

以下は、出すようにしたときの話。

説明を減らすほど、はじめての人の手がかりも減る。
その埋め合わせに、**最初の1回だけ、実際の部品を光らせて順に説明する**
（依頼者の提案・2026-08-27。「代わりに初回時には、各項目を照らしながら
説明するチュートリアルを入れる」）。

- 案内は画面ごと（撮る・パーツ一覧・縫い代・並べる の4本、合計14項目）。
  その画面を**はじめて開いたときだけ**出て、読み終えると二度と出ない
- 読んだかどうかは端末に覚えさせる（`yojaku.tour1.<画面>`）。
  中身を書き替えたときは `Tour.tsx` の `KEY` の番号を上げると、もう一度出る
- 見出しの「？」でいつでも呼び戻せる。1回きりで消えるものに、逃げ場を残すため
- 指す相手は `data-tour="…"` で印を付けてある。
  その画面に無い部品（縫い代つきの型紙には「まとめて」が無い）は、だまって飛ばす
- 書く相手は学生。「わ」「地の目」「みみ」といった言葉そのものは説明しない。
  説明するのは、どこを押せば何が起きるか、だけ

案内があるぶん、**同じことを言う常設の説明は消してよい**。
パーツ一覧の「枚数はできあがりに必要な数」がその一例で、
消すと一覧がちょうど1画面に収まる（案内を止めているいまは戻してある）。

縫い代は、辺のまとまりごとに帯を塗り足して作る（[src/lib/seam.ts](src/lib/seam.ts)）。
このとき**線分の向きは、その線分が属する辺の中だけを見て決める**。

輪郭は3mm間隔で取り直してあるので、角のちょうど上に点が乗るとはかぎらない。
角をまたぐ線分が1本でき、その向きは両側の辺の中間になる。
そのまま法線を取ると、裾のような広い縫い代のときに角が斜めに張り出したり削げたりする
（実際に裾を4cmにして起きた・依頼者の指摘・2026-08-27）。
辺の内側の点だけで向きを測れば、角は実物どおり四角く決まる。
角の点そのものは両方の辺に半分ずつ乗っているので、向きの測定からは外している。

縫い代の札は「わ」ではなく**「わ 0」**と書く（依頼者の案・2026-08-27）。
「わ」と「縫い代 0」が同じことだと、札そのものが言っているので、
文で説明する必要がなくなる。説明を減らすときは、
消した内容を札に移せないかを先に考えること。

**どの画面も、できるかぎりスマホの1画面に収める**（依頼者の指示・2026-08-27）。
下へスワイプしないと操作できない状態は、それだけで使いにくい。

375×812 で測ったはみ出しは、撮る 0・パーツ一覧 21（3個のとき）・縫い代 0・並べる 636。
パーツ一覧の 21 は、案内を出すようにして「枚数」の説明を消せば 0 になる。
並べる画面だけは、生地の絵そのものが 1.5m ぶんの長さを持っているので収まらない。
ここは段の間隔を詰めるにとどめてある。

縫い代の画面は、その中でもきちんと収まるように組んである。
下へスワイプしないと操作できない状態は、それだけで使いにくいため。

- 戻る・型紙の名前・隣の型紙への送りを、いちばん上の1段にまとめてある
- 「まとめて」と「1本ずつ」は、もとは別々の枠だったが、ひとつの枠に入れてある
- 図の高さの上限は `max(140px, min(34vh, calc(100dvh - 33rem)))`。
  「画面の高さから、下の操作のぶんを引いた残り」なので、
  小さい端末では図のほうが縮んで、収まった状態を保てる。
  縮みすぎると辺を押せなくなるので下限も置いてある
- 「わ」の裁ち方を選ぶところも1段。説明は、ふつうでないほう（開いて裁つ）を
  選んだときにだけ出す

縫い代の幅は、よく使う値を札にして並べてあるが、
**札に無い数値を直接入れる欄**も下に置いてある（依頼者の指示・2026-08-27）。
1.8 cm のような指定が出たときの逃げ道で、1 mm 刻みに丸める。
札を増やすと、いつも使う 1 cm や 1.5 cm が探しにくくなるため、
めったに使わない数値はこちらへ回す。
いま入っている幅が札のどれでもないときは、この欄を縫い代の色にして、
その数字がどこから来たのかが分かるようにしてある。
なお「まとめて全部に付ける」ほうは、決まった一覧のままにしてある。

送りは右上（依頼者の指示）。1枚ごとに一覧へ戻るのは手間なため。
最後の1枚まで来たら、そのまま並べるところへ進める。

**「わ」に指定した辺には、作図の記号を辺そのものに付ける**
（依頼者の指示・2026-08-27）。◎ を半分にした形——同じ中心の半円を二重に、
平らな側を辺に伏せ、まるいほうを型紙の内側へふくらませて描く（`SeamEditor` の `foldMark`）。
学校の作図で「この辺は折り山（わ）」を表す決まった印なので、
文字より先にこの形で読み取れる状態にしておく。
辺に沿う向きを `t = (outward.y, -outward.x)` に取ると、
SVG の弧を `sweep=1` で引くだけで内側へふくらむ。
番号のふきだしに添える「わ」の字は、記号と重ならないよう外向きへ押し出してある。

**この記号は、生地に並べた図にも出す**（依頼者の指示・2026-08-27）。
むしろ裁ち合わせ図のほうが本番で、どの辺を折り山に当てているかが図の要になる。
そのため `PlacedPart` は `foldMarksMm` を持つ。辺ごとに **3つの点**
（辺に沿った直径の両端 a・b と、型紙の内側の点 inn）で置き場所と向きを表したもので、
`a`–`b` の長さは `FOLD_MARK_REF_MM` に固定してある。実際に描く大きさは描く側が決める。

向きを角度や法線で持たずに点で持たせてあるのには理由がある。
生地の上では型紙を回したり裏返したりするので、
点にしておけば `orientedPair` の中で裁ち切り線とまったく同じ計算に通せて、
**裏返したときに弧のふくらむ向きが反転する**という間違いが起こらない。
弧のまわり方（SVG の sweep）は `(b - a) × (inn - a)` の符号から毎回決める。
`verify:layout` に、そのまま・裏返し・180度・地の目90度の4通りで
まるいほうが型紙の内側を向いているかを見る検算を入れてある。

「わ」の辺で開いて裁つ設定にしたパーツは、生地の折り山に当てないので記号も出さない。

「わ」の辺を持つパーツには、裁ち方が二通りある（依頼者の指示・2026-08-27）。
生地の折り山に当てて二重のまま裁つやり方と、
**型紙を「わ」の辺で開いて幅を倍にし、一重の生地に裁つ**やり方で、
布としては同じものが取れる。ベルトは後者にすることが多い。
縫い代の画面の下で選べるようにしてあり、開いたほうを選ぶと
生地の折り山は要らなくなる（型紙の中に折り山があるだけになる）。

開いたほうを選ぶと、型紙は本当に「わ」の線を軸として反転し、幅がちょうど倍になる
（`openFold.ts` の `unionWithMirror`。ベルトの例で 26.1 cm → 52.0 cm）。
ただし**開いた形には、中心を示す一点鎖線が要る**（依頼者の指摘・2026-08-28）。
線が無いと、ただ幅の広い長方形にしか見えず、
反転して倍になったことが図から読み取れない。実際そう見えるという指摘を受けた。
しくみは正しく動いていても、**図がそう言っていなければ、まだ届いていない**。

そのため `PlacedPart` は `centerLineMm` を持つ。もとの「わ」の辺を
出来上がり線の外接まで伸ばした線分で（`geom.ts` の `clipLineToBox`）、
「わ」の記号と同じく `orientedPair` の中で裁ち切り線と同じ計算に通す。
描くのは縫い代の画面の下の見本と、生地に並べた図の両方。
一点鎖線（長・短・長…）は作図で中心線を表す決まった引き方なので、
出来上がり線（実線）とも縫い代（別の色）とも読み分けられる。

中心線は型紙の真ん中を通り、地の目線もふつうは真ん中を通るので、
**そのままだと2本がぴったり重なって読めなくなる**。
2本が平行になるときだけ、地の目線を型紙の幅の2割ほど脇へどける
（`LayoutView.tsx` の `grainShiftOf` と `PatternMarks` の `shift`）。
直角に交わるときは1点で交わるだけなので、どけない。

生地の**上下の端はどちらも波線**で描く（依頼者の指摘・2026-08-27）。
どちらもはさみで切った裁ち端なので、下だけまっすぐに引くと折り山に見えてしまう。
折り山にする側だけは、波線ではなくまるみのある角で描き分ける。

**二重になっているところは、下の一枚を2方向にずらしてのぞかせる**
（依頼者の指示・2026-08-27）。折り山の反対側へ少し出すだけでは、
重なっている感じが伝わりにくい。折り山に沿う向きにも `RIM * 1.15`（`UNDER_SHIFT`）
だけずらして、紙を2枚わずかにずらして重ねたときのように角をのぞかせる。
ずらす量は控えめにすること。大きくすると、折り返しではなく
「2枚の別の布」に見えてしまう（依頼者と何段階か見比べて決めた値・2026-08-27）。
下の一枚のみみ（点々）は、**実際にのぞいている側にだけ**描く。

そして**折り山の端では、2枚の裁ち端をひとつの半円で結ぶ**
（依頼者の指示・2026-08-27。学校の裁ち合わせ図と同じ描き方）。
ここが「生地がぐるっと回って戻ってきている」ことを伝える、いちばん大事なところ。

半円の半径 `RHO` は、ずらした量のちょうど半分。中心は上の一枚の裁ち端から
`RHO` だけ先に置く。すると中心から見て、

- 上の一枚の裁ち端
- 折り山
- 下の一枚の裁ち端

の3つがちょうど 90 度ずつ離れた向きにあり、**1本の半円が3つとも接する**。
上の一枚は内へえぐれる四半円（`sheet()` の `hook`）、
下の一枚は外へふくらむ四半円（`foldParts`）を描き、
折り山の線は半円の頂きまで伸びる。2枚合わせて U 字になる。

**折り山の明暗の帯も、その先まで届かせる**
（下の一枚の形を `${gid}-clip` に足してある）。
帯が上の一枚のところで止まると、明かりが角で断ち切られてしまい、
形だけ U 字にしても「回って戻ってきている」ようには見えない。

ここまでは `foldParts` が組み立てる。折り山に沿う向きを u、
折り山から離れる向きを v として書き、最後に画面の向きへ移している
（折り山が左・右・上・下のどれでも同じ式で済むため）。

**この描き方は、どの折り方でも同じように使う**（依頼者の指示・2026-08-27）。
`foldParts` は折り返し（`flaps`）1つにつき1枚の「下の一枚」を作るので、

- 縦わ・片側 … 折り山の下の端で回り込む。面が丸ごと二重なので、みみの側にも `RIM` のぞく
- 縦わ・両側 … 左右2つの折り返しが、**下の端の左右2か所**で回り込む
- 横わ・上端／下端 … 折り山の**右の端**で回り込む。ずらす向きも横になる
- 横わ・両側 … 上下2つの折り返しが、**右の端の上下2か所**で回り込む

回り込む先が縦わなら裁ち端、横わならみみなので、
下の一枚のその端は、縦わのときだけ波打たせ、横わのときは
まっすぐのままピン穴（点々）を並べる。

**二重のところも、生地の色は変えない**（依頼者の指示・2026-08-27）。
以前は面の一部だけを覆う折り返しを `CLOTH_FOLDED` で塗っていたため、
「縦わ・片側は明るいのに、縦わ・両側は暗い」という食い違いが出ていた。
二重であることは、ずらして描いた下の一枚・回り込み・端の線と点々・
「生地が二重」の文字で伝える。
両側から折ってみみが中央で出会う隙間だけは、そこに見えているのが
本当に下の一枚なので `CLOTH_FOLDED` で塗る。

以前は、ずらす量を折り山へ近づくほど 0 に戻す（なだらかに細らせる）やり方で
描いていたが、これは伝わらなかった。なだらかに細らせると
「先が尖っていく」ようにしか見えず、回り込みにならない。
半円ひとつで結ぶほうが、ずっとはっきり読める。

絵についての注意書きは、**絵と同じ枠の中（緑の地の上）に置く**
（依頼者の指示・2026-08-27）。枠の外に出すと画面ぜんぶへの説明に見えて、
どの絵の話なのか分からなくなる。
「型紙の青いふちが縫い代」の一文は、ひとつ前の縫い代付けで済んでいるので置かない。

**「ここで切り分けて、折り方を変える」**（＝区間を増やす）は、
まだ何も置いていないうちは出さず、右寄せの小さな字にしてある
（依頼者の指摘・2026-08-27）。めったに使わないボタンが、
生地の絵と「置くパーツ」のあいだで場所を取っていたため。

折り方は上の1段にまとめてある。折り方のプルダウンの右に、
どこまで折るか（半分に折る／型紙に合わせて）のプルダウンを並べる
（依頼者の指示・2026-08-27）。もとは大きなボタン2つを下の段に置いていたが、
ほとんどの人は「半分に折る」しか使わないので、そのために1段を使わない。

生地の折り方は、平面図と断面図の2枚で同じことを言っている。
両側から折って**みみが中央で出会うとき**は、そこにわずかな隙間を空けて描く
（依頼者の指示・2026-08-27）。突き合わせて描くと二重の帯が1枚の面につながって見え、
そこが端どうしの出会うところだと分からなくなるため。絵のうえだけの隙間で、計算には効かない。

帯の名前は「二重」ではなく**「生地が二重」**と書く。
主語がないと、置いた型紙が2枚という意味に読めてしまうため（依頼者から実際にそう質問された）。
帯が細くて字がはみ出すときだけ短いほうに落とす。

**裏返して置いた型紙**は、白い表ではなく、うっすら斜線の入った「紙の裏」の色で描き、
「裏返し」と書き添える（依頼者の指示・2026-08-27）。形だけでは裏返したことに気づけない。

絵は全部、裁縫室にある物を横から見た形で描いてある（横棒1本＝一重、横棒2本＝二重、
ヘアピン形＝折り山、はさみ＝裁ち端、点々＝みみ）。歯車やフォルダのようなパソコンの記号と、
絵文字は使っていない。詳しくは `Icon.tsx` の先頭に書いてある。

外部の画像処理ライブラリ（OpenCV.js など）は使っていない。
